## Alternatives

| | What | For | Against |
|---|---|---|---|
| **A. | **D. Keep `npm ci`, pinned by lockfile and `--ignore-scripts`** (today) | status quo | no vendored code, Dependabot and `npm audit` work | the problems in the proposal's "Why": network and npm in the user's environment, the auditor's one write, a failure mode, CI install. | **E. **Recommendation: A.** The reason is the supply-chain claim. With A, "these are the bytes the registry serves for `yaml@2.9.1`" is a statement that a third party can check without trusting our build or esbuild: `npm pack yaml@2.9.1`, hash, compare. B turns it into "this is what our pinned build produces", which is weaker and needs more tooling to prove; its one advantage (size) is real only minified, and minified output is the hardest to review. A's cost is 76 files and about 300 KB, which is acceptable next to a 1.6 MB package (see "Size").

## Decisions

**1. Layout and loading.** The files go to `scripts/vendor/yaml/` inside the skill, so every channel carries them: the plugin (a Git checkout of the plugin folder, minus `node_modules`, which `.gitignore` excludes), the CLI (`install.mjs` copies everything except `node_modules` and its marker), and `npm pack` (`files` has `plugins/*/skills/**`, excluding `node_modules`, `test`, `evals`). The folder must not be named `node_modules`. `scripts/lib/yaml.mjs` is one line, `import YAML from "../vendor/yaml/dist/index.js"; export default YAML;`; Node loads a CommonJS default export of a `.js` file whose nearest `package.json` says `commonjs`, which is the vendored `package.json`. A test fails if any other file imports the bare name. *Not verified here:* that a copy without that nested `package.json` fails to load (Node's documented rule says it does; the first red test of task 3.2 shows it).

**2. Selection rule.** Every `dist/**/*.js` file, plus the package's `package.json` and `LICENSE`. Not kept: `.d.ts`, `dist/cli.mjs`, `browser/`, `bin.mjs`, `util.js`, `README.md`. The rule is written in `PROVENANCE.json` so `update` applies it mechanically and `verify --registry` compares exactly those files.

**3. Provenance record.** `PROVENANCE.json` has: `name`, `version`, `tarball` (URL), `tarballSha256`, `integrity` (`sha512-...`, equal to the lockfile's), `license`, `licenseFile`, `selection` (the rule above), `retrieved` (date), and `files` (path and SHA-256 for every vendored file, sorted by path). It is data, not code. It never contains a credential-shaped value (hashes only).

**4. Integrity check.** `scripts/vendor-yaml.mjs` (Node 20, no dependency, `node:crypto` and `node:fs` only):
- `verify`: reads the record, walks `scripts/vendor/yaml/` (without following symbolic links, and refusing any), and fails on a changed, missing or extra file, a version that differs between the record, the vendored `package.json` and the lockfile, an `integrity` that differs from the lockfile's, and any `\r` in a file whose recorded hash has none (the CRLF case). It prints file names, never contents.
- `verify --registry`: `npm pack yaml@<version> --ignore-scripts` into a new empty temporary folder (`npm pack` downloads and does not run package code), unpacks with `tar` (or reads with the same selection), compares the tarball hash to the record, then each kept file byte for byte with the vendored copy. Nothing from the tarball is executed. Needs network; runs in the scheduled workflow and, optionally, in CI on pull requests that touch the vendor folder.
- `update <version>`: the only writer. Downloads, checks the registry's integrity string against `npm view` (a second, independent answer from the registry), applies the selection rule, writes the files, `PROVENANCE.json` and the `devDependencies` pin and lockfile entry, prints a summary (files added, removed, changed). Refuses to overwrite files that differ from the old record without `--force` (a hand edit of the vendor is a finding, not an update).
- The offline `verify` is also run by a test (`test/vendor.test.mjs`) so a plain `npm test` catches drift on every platform.

**5. Supply-chain compensation (the vendor is outside `npm audit`).** In order of strength:
1. *Identity*: the per-file hashes and the tarball hash (Decision 3, 4). One changed byte fails CI.
2. *Visibility to scanners*: keep `yaml` 2.9.1 as a `devDependency` with its lockfile entry. Dependabot security alerts, the dependency graph and `npm audit` read the lockfile, so a published advisory for 2.9.1 still shows on the repository. A parity test fails when the oracle's version differs from the vendored version, so a Dependabot version-update pull request (needs `.github/dependabot.yml`, which does not exist today; Q4) cannot be merged green until `update` has run in it.
3. *A watcher that does not depend on settings*: `.github/workflows/vendor-watch.yml` (weekly and on demand; `contents: read`): runs `verify --registry`, asks the OSV API (`api.osv.dev`, query by ecosystem `npm`, package `yaml`, the recorded version) for known advisories, and compares the recorded version with `npm view yaml dist-tags.latest`. It fails on a changed tarball or an advisory, and only warns (a notice in the job summary) on a newer version.
4. *Registry signature*: `npm audit signatures` over the oracle install in the parity job (today: "1 package has a verified registry signature"; no provenance attestation exists for this package, so the check says less than it does for packages that have one, and the document does not claim otherwise).
5. *Human step*: `update` prints the release notes URL and a file diff summary; the pull request template item (below) asks the reviewer to read the diff of `dist/`.

Limits that remain, said plainly: the first hash is taken from the registry at vendoring time (trust on first use); the lockfile's older integrity string, committed before this change, is a second point that the registry served the same bytes earlier, which is why `integrity` must equal it. There is no source-to-tarball proof (no provenance, and rebuilding upstream's rollup output from the tag is not attempted here); a compromised release of `yaml` that is vendored by `update` would be vendored. The scheduled workflow narrows the window in which an advisory is unknown; it cannot close it.

**6. Updates of `yaml`.** One command, `node scripts/vendor-yaml.mjs update <version>`, in a pull request that shows: the file diff summary, the golden diffs (if behavior changed, the parity corpus shows it), the lockfile change. The pull request template's checklist is not edited here; `CONTRIBUTING.md` gains a short "Updating the vendored yaml" paragraph (task 7.2). Security updates use the same path, with the scheduled workflow or Dependabot's alert as the trigger.

**7. The guard and the agent (scope: in this change).** Once the engine needs no install, `npm ci --prefix <skill folder> --omit=dev --ignore-scripts` is dead code with a real cost: it is the only allowlisted shape that writes, uses the network and reads the user's npm configuration (`userconfig`, registry, environment variables apply even with `--prefix`, as the guard's own comment says), and it is what forces the guard's `isEngineDir`, the `--prefix` branch of `pathsOf`, the "not inside `cwd`" rule for a folder that is not an engine file, and 29 lines of tests. Leaving it allowed would keep an unused write path in a read-only agent. **Recommendation: remove it in the same change**, in the same release as the vendored parser, because a guard that still permits `npm` while the agent no longer needs it is exactly the kind of surplus authority that the `fix-stacks-auditor-*` changes spent three review cycles removing, and because splitting it would need a second release for a deletion. The change is small and mechanical: delete the shape from `SHAPES`, `case "npm"` (falls to the default denial), `isEngineDir`, the `npm` branch of `pathsOf`, and the tests that pin it; add tests that `npm ci --prefix <trusted folder> ...`, `npm install`, `npx yaml` are denied by the default rule. The agent's step 3 ("Dependency") is deleted, its command list loses one line (the guard test that keeps the lists equal fails otherwise, which is the safety net), and the sentence "This is the only write you may make" goes with it: the auditor then writes nothing, and the report line "No file in the repository was changed" no longer needs the "Mention the engine's `node_modules` if you installed it" clause. The spec delta changes "Auditor subagent" and "Command guard" accordingly. **Compatibility:** a user whose user-scope copy of the skill predates this change (no vendor folder, no `node_modules`) and who updates the plugin gets a guard that cannot install the package; the auditor prefers the plugin's own copy first (`ls -d` order), so plugin users are unaffected; for a stale user-scope copy the auditor must say "update the skill" and not try anything else (a sentence in the agent's step 2 and in `references/traps.md`, not in `SKILL.md`). That is the one real cost of removing the exception, and it is the same class of problem the 0.2.0 users already have.

**8. Context budget.** `SKILL.md` is 13,947 bytes (3,487 of 3,500 estimated tokens in `test/budget.test.mjs`; `scripts/context-budget.mjs` reports the same, with `agent:stacks-auditor` at about 6,134 tokens of its 9,000). It cannot grow. The only edit is line 28 (162 bytes with its newline), which becomes: `1. **No install step.** Node.js 20 or later is required; the engine's one dependency is vendored in `scripts/vendor/`.` (119 bytes, counted with `wc -c`), a net change of -43 bytes. The reason, the provenance and the update procedure go to `references/traps.md` (not preloaded) and to `CONTRIBUTING.md`. A test pins `statSync(SKILL.md).size <= 13947` for this change in addition to the existing 3,500-token budget, so a later edit cannot spend the saved bytes without a decision. The agent file shrinks too (step 3 and one command line go), which lowers its preload estimate.

**9. CI and tests.**
- Job `azure-terraform-stacks` (Node 20, 24, Ubuntu): drop `npm ci`; `npm test` runs `node --test test/*.test.mjs` without `node_modules` (this is the proof that no test needs the package). Add a matrix entry for Windows (Node 24) that runs the same suite; if some existing test fails there for a reason unrelated to this change (never measured: the job runs only on Ubuntu today), the Windows run is limited to `test/vendor.test.mjs`, `test/yaml-parity.test.mjs` and the engine's golden tests, and the reason is written in the pull request (the CRLF checkout is the risk this run exists for, and `windows-latest` does check out with `core.autocrlf` as Git for Windows sets it; `.gitattributes` `-text` is the guard).

## Proof plan

**P1. Behavior does not change.**
1. *Baseline*: the 164 tests pass on `main` with the install (run, 2026-11-25). After the change they pass with no `node_modules/` anywhere (a clean checkout; the CI job without `npm ci`; locally `rm -rf node_modules` first). Golden files for `scaffold`, `check` and `audit` are byte-for-byte unchanged (`git diff --stat -- test/golden test/golden-findings.json` is empty).
2. *Identity beats imitation*: under A, parity of the parser is first a byte comparison (`verify --registry`), which is stronger than a behavioral test. The behavioral tests then guard what A can still get wrong: the loading mechanism (nested `package.json`, the facade), line endings after checkout, and the engine running with no `node_modules`.
3. *Golden corpus* (`test/yaml-corpus/`, committed, with `golden.json`): runs without the oracle on every platform. Cases (each is one file or one string): alias bomb (nine nested levels of nine aliases: the expected result is the package's own refusal, `ReferenceError: Excessive alias count indicates a resource exhaustion attack`, measured in the scratch run); a small reused anchor and alias (no refusal); `!custom` and `!!str` tags (an unresolved tag is a `TAG_RESOLVE_FAILED` warning through `process.emitWarning`, and `parse` still returns the string; the test captures `process.on("warning")`); the YAML 1.1 merge key `<<` (measured: kept as a plain key `"<<"` under the 1.2 core schema); duplicate keys (a parse error, `Map keys must be unique`); two documents given to `parse` (error `Source contains multiple documents`); `---` and `...` separators through `parseAllDocuments`; CRLF, lone CR, byte-order mark (the BOM and CRLF cases returned the same values in the scratch run); tabs as indentation (error); an unknown alias (error); a manifest with comments, round-tripped by `parseDocument(...).toString()` after `createNode` with `flow = true` (the `add-stack` path); a flow collection nested 1,000 deep (measured: a `YAMLParseError` "Maximum call stack size exceeded"; caught by the engine's `try`) and a block mapping 1,000 deep (a `YAMLParseError`); a 1 MiB scalar. For each: the serialized result of `parse`, of `parseDocument(...).toString()` and of `parseAllDocuments(...).map(toJS)`, plus, for errors, `name`, `code`, `message` and `linePos`. Anything that can exhaust memory runs in a child process with `--max-old-space-size` and a timeout, and the expectation is the exit status and the error name. *An observation to keep, not to fix here:* in the scratch run (`yaml` 2.9.1 from the lockfile, Node 22.23.5) a process that called `YAML.parse` on a 1,000-deep flow sequence (a caught `YAMLParseError`, stack overflow) and then on a 10,000-deep one aborted with exit status 134 (V8 `RegExpCompiler Allocation failed`, reproduced with `1000,10000` and `1000,1000,10000`); the 10,000-deep input alone, in a fresh process, exits 0. Two such files (a 1,000-deep and a 10,000-deep one in `.github/workflows/`) did not abort `node scripts/stacks.mjs audit --root ... --json` (exit 0), so no impact on the engine was shown; the cause is not understood. It is the same code before and after vendoring, so it is not a regression risk of this change. It argues for running those corpus inputs one per child process, and for a follow-up look at hostile-input limits (task 10.3).
4. *Differential* (`test/yaml-parity.test.mjs`, needs the oracle): the same corpus plus every `.yaml` and `.yml` under `test/fixtures/` and `test/golden/`, through the facade and through `import("yaml")` of the installed package, compared as serialized values; fails if `oracle.version !== PROVENANCE.version`. Prior art for the method: the scratch run compared the package, an unminified bundle and a minified bundle on ten inputs (alias bomb, CRLF, BOM, tags, two documents, duplicate keys, merge key, a syntax error, tabs, an unknown alias) with three operations each: all identical. That experiment is evidence that the method works, not the test.
5. *No ambient package*: a test copies the skill (without `test/` and `node_modules/`) to a new temporary folder outside the repository, with `NODE_PATH` unset, and runs `check-manifest` and `audit` there; and a static test scans every `.mjs` outside `scripts/vendor/` for a bare `yaml` import.

**P2. Integrity.**
1. `node scripts/vendor-yaml.mjs verify` exits 0 on the committed state, on Linux and Windows.
2. *Mutation tests* in `test/vendor.test.mjs`, each on a temporary copy of the vendor folder and the record, never on the committed files: flip one byte of one file; delete a file; add an extra `.js` file; change a hash in the record; change the version in the record; rewrite one file with CRLF; replace a file with a symbolic link. Each must exit 1 with the file's name. *Hand check recorded in the pull request*: edit one byte of `scripts/vendor/yaml/dist/index.js` in a branch, push, and show the red CI job; revert.
3. *Registry*: `verify --registry` exits 0 on the committed state; with a corrupted record it exits 1 (the test uses a local file as a fake registry through an `--tarball <path>` option, so the unit test needs no network).
4. *Scheduled workflow*: run once by hand (`workflow_dispatch`) before merge; the result is linked in the pull request.

## Risks and residual limits

| Risk | Mitigation | Residual |
|---|---|---|
| The vendored copy is tampered with after merge | per-file SHA-256, offline `verify` in every `npm test`, branch protection (`docs/aep/repository-protection.md`) | an attacker who can also edit `PROVENANCE.json` in the same commit; review of the record's diff is the control; CODEOWNERS on `scripts/vendor/**` is an option (Q8) |
| A compromised upstream release is vendored by `update` | the scheduled advisory lookup, `npm audit signatures`, the human read of the diff, an exact version pin | no source-to-tarball proof exists for this package (no attestation); first use is trusted |
| A vulnerability in `yaml` is published and nobody updates | Dependabot alert on the devDependency (if the repository setting is on), weekly OSV lookup | the repository is maintained by one person; the window is the time to read the alert |
| Windows or an `autocrlf` checkout rewrites vendor line endings | `.gitattributes` `-text`, a CRLF mutation test, a Windows CI run | a user who copies the folder by hand with a tool that converts line endings; the engine would still run, and the first `verify` would say what changed |
| A stale user-scope copy of the skill next to the new plugin | the plugin's copy is searched first; a "Cannot find package 'yaml'" note in `references/traps.md`; the agent says "update the skill" | a user who only has the stale copy and no network sees an error instead of an install; the same user was already stuck offline |
| `scripts/vendor/` is large for a reader of the skill folder | `PROVENANCE.json` and `references/traps.md` say what it is; `SKILL.md` names it in one line | 76 files in a folder that was 7 before (`scripts/lib` has 15 modules) |
| The facade hides an accidental second copy of `yaml` | the no-bare-import test and the no-`node_modules` test | none known |
| `yaml` 3.x (`next` tag, 3.0.0-2) changes behavior on a later update | `update` is explicit; the golden corpus shows differences; not part of this change | planned, not scheduled |
| The guard's removal of `npm` surprises someone who relied on it | stated in the agent, `references/traps.md`, CHANGELOG | the 0.2.0-class problem for stale copies |
| Hostile YAML in an audited repository still reaches the parser | unchanged by this change; the engine already parses in `try` (discover, rules, check); the corpus pins the behavior | a repeated deep-nesting parse in one process aborted Node in a scratch run, and did not through `audit` (see P1.3); not understood; follow-up, not a blocker |

## Alternatives rejected

- **C, a minimal parser.** Rejected above: a new attack surface to save 300 KB.
- **E, a separate package.** Rejected above: no install step is removed.
- **B as the recommendation.** Considered seriously: if the maintainer prefers a single file and a smaller tree, B (unminified, `.cjs`, pinned esbuild, CI rebuild-and-compare) is a defensible choice at the same size, with a weaker identity claim and one more tool to trust. Q1 asks.
- **Keep the `npm` shape in the guard "for one more release".** Rejected: it leaves the only writing shape allowlisted for no user who needs it; the stale-copy case is handled by a message, and a second release for a deletion buys nothing.
- **Vendor with no record and no check** ("copy `dist/` and move on"). Rejected: that is the loss of traceability that the maintainer ruled out.
- **A git submodule or `git subtree` of upstream's repository.** Rejected: it vendors source, not the published artifact, and the engine would need upstream's build; the clone would also run from the user's network.
- **Vendoring the `browser/` ESM build** (a smaller loading story: ESM, `type: module`, no nested `package.json` trick). Not chosen, not measured for equivalence: the Node export condition points to `dist/` (CommonJS), which is what the package's own tests and the lockfile-installed engine exercise today; switching to the browser build changes which code runs, and `log.js` differs (the Node build uses `process.emitWarning`, the browser build `console.warn`: measured with `diff`). It would break the "same code as today" claim.
