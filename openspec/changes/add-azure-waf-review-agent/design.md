### Decision 1. Packaging: one new plugin, with the agent and two skills

| C. Plan C (last resort, needs maintainer approval): move the three skills into one plugin. ### Decision 3. The agent, its tools and how to limit them

The agent needs five capabilities: read files (`Read`, `Grep`, `Glob`), call the Azure MCP Server (read-only), run the engines of the skills, write `assessment.json`, and nothing else. Options:

| Option | What the agent holds | Pros | Cons |
|--------|---------------------|------|------|
| **T1. Guarded Bash for three fixed engines, guarded Write (recommended)** | `Read, Grep, Glob, Write, Edit, Bash, mcp__plugin_azure-waf-review_azure__*`; a plugin `PreToolUse` guard: `Bash` allows only `node <waf.mjs> <sub>`, `node <assess.mjs> <sub>`, `node <diagram.mjs> build`, `ls -d`, `test -f/-d`, `node --version`; `Write`/`Edit` only inside `waf-review/<run>/`, never `collected/` or `.state/` | Same proven pattern as `stacks-auditor` (guard shapes, trusted-engine origin, no engine inside the audited root). The **catalog fixes what the collector can ask**, so the agent never composes an `az` or KQL string: the part of the old allowlist that took three review rounds (free path and argument shapes) shrinks to "subcommand names and `--out` inside the run folder" | Still the Bash tool and a hook that fails open if Node cannot start it or an administrator disables plugin hooks; three engines instead of one. Write is a new surface (path rules) |
| T2. No Bash: the collector is run **by the user**, the agent only reads files | `Read, Grep, Glob` plus MCP | Smallest surface; credentials and `az login` stay with the user | The report pipeline (`assess.mjs`) also needs a shell; the user would run 6 to 8 commands by hand. Defeats "an agent that verifies and brings results". Kept as the **fallback mode** (`--collect-only` by the user; the agent starts at "analyze") |
| T3. The collector as an own MCP server (one tool `collect(check_id)`) | `Read, Grep, Glob` plus two MCP servers | No Bash for collection; the tool schema is the allowlist | New code (JSON-RPC or an SDK dependency, which this repository avoids), a second long-lived process holding credentials, still Bash for `assess.mjs`. Deferred, not rejected: revisit when the catalog stabilizes |
| T4. The agent returns JSON in its final message and the main conversation writes the files | `Read, Grep, Glob` plus MCP | No `Write` for the agent | Puts the whole assessment in the main context, the opposite of isolation; loses incremental persistence |

**Does a fixed catalog avoid free Bash? Partly.** It avoids free *commands to Azure*: the agent cannot compose `az`, KQL or REST. It does not remove the need for the shell tool, so a guard remains. The honest gain is a much smaller and more testable guard (Decision 3, "Guard rules"), and no `az` in the guard's allowlist at all, because the engine spawns `az` itself with constant arguments.

**The `assess.mjs` subcommands the guard allows** are `status`, `init`, `inventory`, `verify`, `classify`, `check`, `review` **without `--approve`**, `render --unreviewed` and `finish`. `review --approve` is denied to the agent on purpose (the skill says the agent never approves); it runs in the main conversation after the user's explicit yes. `capture` is not needed because collected data is already sealed by the collector.

**Guard rules (summary; the spec has the full list).** The guard acts only when `agent_type` is `azure-waf-reviewer` or `azure-waf-review:azure-waf-reviewer` (the precedent shows the namespaced value is what a plugin subagent reports), allows only the shapes above, resolves the real path of every engine and accepts it only from the plugin's own skill folders or the user's skills folders (never inside the working directory or any `--root`), rejects shell metacharacters wholesale (no quotes, `$`, redirects, pipes), and for `Write` and `Edit` resolves the real path and allows it only below `<cwd>/waf-review/` excluding `collected/`, `.state/` and `.gitignore`. It also denies MCP calls whose namespace is not on the allowlist (defense in depth for `--namespace`). It **fails open** if Node cannot start the script; the agent file and README say so and give `permissions.deny` rules for people who need more. A test keeps the shapes in the agent file equal to the guard's list (the precedent's `guard.test.mjs`).

**Output location and who writes.** Engines write the run folder `waf-review/<run-id>/` (`<run-id>` = UTC timestamp) under the working directory; `init` creates `waf-review/.gitignore` containing `*` (the folder ignores itself, so a private tenant dump cannot be committed by accident and no `.gitignore` edit is needed). The model writes only `assessment.json` (and its pillar fragments, if any) and `questionnaire.answers.json`; everything else is engine output. Layout:

```text
waf-review/<run-id>/
  .gitignore                      (engine; content "*")
  run.json                        (engine: scope, consent record, versions, catalog hash)
  collected/                      (collector only; model Write denied)
    manifest.json                 (sealed entries per check)
    <check-id>.jsonl              (one resource per line, redacted)
    summary/<pillar>.md           (engine-written, at most about 1,500 tokens each)
  coverage.json  coverage.md      (engine: per check and per pillar)
  topology.json                   (engine, from collected data)
  diagram/<level>-<name>.drawio   (architecture-diagram engine)
  questionnaire.json              (engine) and questionnaire.answers.json (user, or model transcribing the user)
  assessment.json                 (model, assessment-report schema)
  .state/ report/                 (assess.mjs)
```

### Decision 4. Context at tenant scale

The model must never hold the tenant in context. The design:

1. `waf.mjs plan` writes `run.json` from the user's answers (scope: root management group or list of subscriptions; pillars; redaction level) and lists the subscriptions **visible** to the identity. The user confirms the count (**consent interrupt**). This also defends against the silent partial result of Resource Graph (claim 12): a lower count than expected is reported as `scope-incomplete`, not as a clean tenant.
2. `waf.mjs collect --pillar <p>` runs the catalog checks of one pillar: one Resource Graph query per check at tenant scope (management group scope or the subscription list), paging with `$skipToken` to disk, bounded by limits (Decision 5). It is **resumable** (`manifest.json` lists finished checks; `--resume` skips them) and idempotent.
3. The engine writes `summary/<pillar>.md`: per check, state, counts (evaluated, failing), the top 10 offenders (ARM ID, one key attribute) and the line numbers. That, not the raw data, is what the model reads. Drill-down uses `Read` with offset and limit on a JSONL file (one resource per line, so a line is a stable citation).
4. The model works **pillar by pillar** and persists after each pillar (`assessment.json` is updated with `Edit`); an interrupted run resumes from the file and the manifest. Findings for a failing check are drafted by `waf.mjs map` (deterministic: evidence entries, WAF reference, check ID) and the model adds impact, likelihood, rationale, recommendation and narrative.
5. Context cost is **sublinear in resources** by design: it grows with the number of checks and with the cap on offenders listed, not with resources. This is a design property to be measured (estimate below, test in manual run M-7).
6. Sub-subagents per pillar are **not** used: whether a subagent can spawn another was not verified, and one agent with files as state is simpler.

### Decision 5. The check catalog and the collector

**Format** (`catalog/<pillar>.json`, JSON because the repository has no YAML dependency outside `azure-terraform-stacks`; a schema `catalog/check.schema.json` validates it):

```json
{
  "id": "SE-NET-001",
  "pillar": "security",
  "title": "Storage accounts allow public blob access",
  "waf": [{ "id": "SE:06", "framework": "azure-waf", "docDate": "2026-06-26", "url": "https://learn.microsoft.com/azure/well-architected/security/networking" }],
  "chain": ["collector", "mcp", "questionnaire"],
  "sources": {
    "collector": { "kind": "arg", "scope": "tenant",
      "evaluated": "resources | where type =~ 'microsoft.storage/storageaccounts' | summarize n=count()",
      "violations": "resources | where type =~ 'microsoft.storage/storageaccounts' | where properties.allowBlobPublicAccess == true | project id, name, subscriptionId, resourceGroup, location, publicAccess=tostring(properties.allowBlobPublicAccess)" },
    "mcp": { "namespace": "storage", "command": "account get", "equivalence": "per-subscription, partial" },
    "questionnaire": { "id": "Q-SE-NET-001", "text": "..." }
  },
  "proves": "The account setting that allows anonymous reads of blobs is on.",
  "doesNotProve": "That any container is actually public, or that data is sensitive.",
  "outputFields": ["id", "name", "subscriptionId", "resourceGroup", "location", "publicAccess"],
  "redact": [],
  "limits": { "maxRows": 20000, "maxPages": 20, "timeoutSec": 30 },
  "requires": ["Reader"],
  "severityHint": { "impact": "high", "note": "input to the model, not a severity" }
}
```

Rules: every check has a `waf` mapping (a WAF recommendation ID with the doc date) or the explicit value `"waf": []` with a reason (a landing zone or hygiene check); `outputFields` is a closed list (anything else the query returns is dropped); `violations` queries must pass an in-house **KQL allowlist** (starts with a documented table name, only read operators such as `where`, `project`, `extend`, `summarize`, `join`, `mv-expand`, `order by`, `take`; no `externaldata`, no `evaluate`, no `;` batches); `kind` is `arg`, `rest-get` (a fixed URL template with `api-version`, GET only) or `az-read` (a fixed argv template, for example `az account list`), and the engine refuses any other kind; every catalog entry has a stable `id` and the catalog has a version and a SHA-256 recorded in `run.json`.

**Result states per check:** `fail` (violations > 0), `pass` (evaluated > 0 and violations = 0), `not-applicable` (evaluated = 0, never reported as pass), `not-verified:no-permission` (HTTP 403 or a visible-scope mismatch), `not-verified:scope-incomplete`, `not-verified:no-api` (nothing in the chain can read it), `not-verified:timeout` (30 s query limit, retried once with a narrower scope per subscription), `not-verified:truncated` (limit hit; offenders are a sample), `not-verified:error` (message class only), `needs-questionnaire`, `answered` (questionnaire).

**Execution.** `az` is spawned by the engine with `execFile` and **constant argument vectors** (no shell, no user input in an argument; the KQL goes in a request body file written by the engine), for example `az rest --method post --url https://management.azure.com/providers/Microsoft.ResourceGraph/resources?api-version=2022-10-01 --body @<file>`. The URL prefix is checked against an allowlist (`https://management.azure.com/`), the method against `GET` or the one documented read-only `POST` of Resource Graph, and a response is read, never stored raw (only redacted, projected fields are written). **No `az login` by the agent**: if there is no valid login the engine stops with exit 2 and the instruction for the user. Windows: spawning `az.cmd` needs special handling in Node (from the author's knowledge of Node security releases, **not verified here**: a `.cmd` cannot be started with `shell: false` on current Node versions); the engine resolves `az` and, only on Windows, starts it through the shell **with constant arguments**; this is risk R5 and manual test M-8.

**Sealing.** `collected/manifest.json` has, per check: `checkId`, `catalogSha256`, `querySha256`, `startedAt` and `finishedAt` (UTC), scope (`managementGroup` ID or subscription ID list hash), `visibleSubscriptions` count, pages, rows, `truncated`, the SHA-256 of the `.jsonl`, the `az` version and the engine version. Raw API responses are not kept. The manifest is tamper-**evident** against accidents (hash checks), not tamper-proof against an actor with write access, like the existing gates.

**Redaction (default, before anything is written):** properties known to carry secrets are never selected (`properties.siteConfig.appSettings`, connection strings, `primaryKey`, `secondaryKey`, SAS, `administratorLoginPassword`, certificate material); tag **keys** are kept and tag **values** are replaced by a short hash except for an allowlist of non-personal keys (`env`, `environment`, `tier`, `criticality`, `workload`, `costcenter`), since owner tags often hold e-mail addresses; every string value goes through the repository's secret scanner (`assessment-report` `scripts/lib/secrets.mjs` is the reference; the collector ships its own copy with a parity test) and a match replaces the value with `[redacted:<kind>]` and counts toward `redactions` in the manifest. Identity names appear only as principal IDs (ARM already returns GUIDs for role assignments; display names are not requested).

### Decision 7. Evidence, confidence and the cap for tool output

**Evidence for a sealed datum.** A failing check writes offenders as JSONL lines; each line starts with the ARM ID. `waf.mjs map` produces, per failing check, an evidence entry of kind `file` of `assessment-report`: `path` = `collected/<check-id>.jsonl` (relative to the assessed root, which is the run's `collected/` folder), `startLine`/`endLine` = at most five offender lines, `quote` = those lines. The citation therefore carries the ARM ID, the check ID (file name), the query and time (in `manifest.json`, named in the finding's `rationale`), and the SHA-256 of the file (the verifier's `drift` check). For "no resource violates" the check state `pass` with `evaluated` > 0 is cited as an `absence` evidence (scope `collected/<check-id>.jsonl`, pattern `^\{"id":`) only when the file is empty after a non-empty evaluated count, and is worded "not found in <scope>", never "does not exist". `assess.mjs verify` re-reads the lines: that is the deterministic verifier, unchanged.

**What the verifier cannot do, and who can.** Re-running a query is a network call to a private tenant; **CI never does it, and `assess.mjs` has no network code**. "Re-verifiable by the user" is defined as: the user (not an agent) runs `waf.mjs reverify --check <id> [--resource <ARM ID>]`, which re-runs the one catalog query, compares by ARM ID with the sealed lines and writes `reverify/<id>.json` with `match`, `changed` (fields differ), `gone` (no longer returned) or `error`, plus the user's UTC time. The agent's guard denies `reverify` (it needs the user's login and intent). `reverify` output is an extra evidence of kind `statement` (source: the user's role, date) so the existing rules count it as an independent source.

**The cap rule (answers the pending item of `add-assessment-report-skill`: confidence cap for tool output).** Objective, in three lines, applied by the new skill's `map` step and checked by its tests:

| Evidence source | Evidence kind in `assessment.json` | Resulting confidence (by the existing rule) | Severity ceiling |
|-----------------|------------------------------------|---------------------------------------------|------------------|
| Collector-sealed JSONL line (manifest hash and catalog hash valid, produced by the engine, `collected/` not writable by the model) | `file` | `verified` | **High**; **Critical only with a passing `reverify` by the user** (recorded in the finding's `rationale`, since the evidence schema has no free-form field) |
| MCP answer typed by the model (no file; the Azure MCP returns text into the context only) | `statement` with `source` `azure-mcp:<namespace>/<command>` and the call time | `reported` (one source) or `corroborated` (two independent sources) | Medium |
| Questionnaire answer by the user | `statement` with `source` the answerer's role | `reported` | Medium |
| MCP answer **and** sealed line for the same check and ARM ID | both | `verified` through the sealed line; the MCP item is listed as corroboration | as the sealed row |
| Nothing | none | `unverified`: only under "Not verified" | n/a |

Why this is defensible: the existing rule caps any non-machine-checked source at Medium and the verifier only proves provenance, not meaning. A sealed line is machine-checked *as a line of a file the model could not write*; it still does not prove the claim is a WAF violation (the catalog's `doesNotProve` text is printed in the finding). Critical requires a human-triggered re-execution because a wrong Critical finding about a production tenant costs most. The rule is local to this capability so `assessment-report` stays unchanged; the maintainer may adopt a general form for its `output` kind later (follow-up, Question Q9): "an `output`/`url` evidence is capped at `reported` unless a registered producer manifest seals it".

**Honesty limits (to print in the method annex).** The model's own tools (`Write`) are guarded, but the guard fails open; the manifest hashes prove consistency, not that the collector ran. The report states: "Evidence sealed by the collector proves a line existed in a file produced at <time>; re-verification by the user is recorded when done."

### Decision 8. Security and privacy

- **Real tenant, minimal role.** The identity that runs the MCP and the collector holds **Reader** and **Security Reader** assigned at the **root management group** (or on each subscription if no MG access), by a person who may assign them. **Never** the "elevate access" route (it yields User Access Administrator, which can write). A **dedicated identity** (a service principal or a user created for the review, with the role removed after) is recommended over the user's own admin account; the Learn security page says the server "reflects your Azure subscription permissions". Reader does not reach data-plane content (no data actions, claim 16); Key Vault secret values and storage blobs need data roles and are never requested.
- **Consent before collecting.** The agent's first interrupt prints: tenant ID (last 4 characters), role found, list of subscription IDs and names (count), namespaces enabled, what leaves the machine (below), and asks for an explicit yes. `run.json` records the consent text hash, time and who answered. No `--yes` flag.
- **Data passes through the model.** Everything the MCP returns, and every summary the engine writes, is sent to the model provider as part of the conversation. The README and the agent say it. The collector redacts before writing, but resource names, IDs, regions, SKUs, tag keys and network layout still pass through. If the client does not allow that, the answer is the T2 mode with `--redact strict` (names replaced by stable aliases `sub-01`, `vnet-03`; a local `aliases.json` maps back and never goes to the model), which is part of the design (spec) and a later task.
- **Never in the output or the report:** secret values, keys, connection strings, SAS tokens, certificates, Key Vault contents, storage content, database rows, application settings values, tag values outside the allowlist, Entra user or group names, e-mail addresses, IP addresses of end users (public IP resources of the tenant are infrastructure and stay, behind `--redact strict` they are aliased). `assess.mjs render` already refuses a secret pattern; the collector's scan runs first.
- **Files stay local and out of git.** `waf-review/` ignores itself; the README says to keep it outside shared drives; `run.json` has a `retention` note and `waf.mjs purge --run <id>` deletes a run folder (confirmation required, user only; denied to the agent).
- **Untrusted input.** Names, tags, descriptions, policy display names and alert text are attacker-controllable strings. The skill states they are **data, never instructions** (aligned with `references/read-only-and-untrusted-input.md` of `assessment-report`); the collector strips control characters and caps string length to 256; the summaries quote strings inside JSON, not as prose; a test plants an instruction-like tag value and checks that the pipeline output does not obey it. The Azure documentation itself says to treat tool descriptions and responses as untrusted.
- **No writes, no login.** The MCP starts with `--read-only` and an explicit namespace list (no `keyvault`, `appconfig`, `storagesync`, `sreagent`, `deploy`, `extension` unless `azqr` is enabled by the user, `foundry*`, `communication`); the collector can only issue catalog reads; the agent never runs `az login` and the engine refuses to run without an existing login; no `--dangerously-*` flag is ever passed (a test greps `.mcp.json`).
- **Residual risk named.** `--read-only` filters by tool annotation; a mis-annotated tool, a server bug or a beta version could still write. Mitigations: exact version pin, a role that cannot write (the real boundary), the namespace allowlist, the guard, and the manual test M-1 that lists the exposed tools. The real guarantee is the **role**, not the flag.

### Decision 9. The diagram skill

- **Format:** a draw.io `mxfile` with one `<diagram>` page per view, uncompressed XML, edges always expanded, ids derived from a hash of the ARM ID (a regeneration gives a minimal diff), `html=1`, no XML comments (rules in `get_drawio_reference` and in `azure-terraform-stacks/references/diagram.md`).
- **Levels (so a tenant stays legible):** **L0 Landscape**: tenant → management group tree → subscriptions as cards (resource count, finding counts by severity, coverage badge). **L1 Subscription** (one page per subscription, capped at the 12 largest plus an "others" aggregate): resource groups collapsed into containers with resource-type counts and the top N resources by finding count. **L2 Network**: hub-spoke view across subscriptions: VNets with subnets, peerings (edges), gateways and firewalls, Private Endpoints and Private DNS zones, derived from `resources` and `networkresources`. Optional **L3 Workload** only if the plan names a tag key that groups resources. Hard caps: 80 nodes and 120 edges per page (an assertion in the generator); beyond the cap a "+N more" node with the count is drawn and the full list goes in `topology.json`.
- **Deterministic layout by script, not by the model.** A tenant diagram is the kind where model-placed coordinates drift, overlap and differ between runs. The generator places nodes by a layered algorithm (tree rows for MG levels, grid columns for children, fixed 10 px multiples) so the same `topology.json` always yields the same bytes. The model is allowed to choose the level, the title and short annotations through `topology.json` fields; it never writes coordinates. Layout by model is **rejected** (not reproducible, not testable) except for an optional "polish" pass the user may request.
- **Design system** (from the project `CLAUDE.md`): `background #0b1326` with `adaptiveColors="none"`; surfaces `#171f33` and `#222a3d`; borders `#45464d`; text `#dae2fd`, secondary `#c6c6cd`; accents `#2fd9f4`, `#7bd0ff`, `#5bbfae`, `#8dc63f`; fonts `Space Grotesk` for titles and `Manrope` for text, `Geist Sans` fallback (draw.io `fontFamily` takes one name, so the label style sets `fontFamily=Manrope` and the fallback is documented in the legend and the file `<diagram>` name; if the user lacks the fonts the editor substitutes). Rounded panels (`rounded=1;arcSize=8`), the discreet cyan glow of the design system has no draw.io style key that was verified here, so it is approximated by `strokeColor=#2fd9f4;strokeWidth=2` on the highlighted container (a documented approximation). Contrast is checked by the same WCAG routine as the stacks generator (text ≥ 4.5:1 on surfaces).
- **Severity colors.** The project palette has accents but no red or amber. Severity is encoded by a **badge letter and fill step inside the palette** (`C`, `H`, `M`, `L` in four accent or surface steps) and by line style, never by color alone; whether a status color outside the palette is allowed for badges only is Question Q6.
- **Icons.** A closed map from resource kind to a built-in `img/lib/azure2/...` stencil, ported from `azure-terraform-stacks/diagram/icons.json` for the kinds used by the catalog; a parity test fails if a path in the new map is absent from the stacks map or from draw.io's own library list when available; an unknown kind draws a labeled rounded box (never a guessed shape, which renders blank). `search_shapes` returned styles with external `https://app.diagrams.net/...svg` URLs; the generator uses the built-in `img/lib/azure2` relative paths so the file works offline in the desktop app and sends no tenant data anywhere. The Azure icon terms apply (do not reshape icons).
- **Validation** (`diagram.mjs check`): well-formed XML by an in-house tokenizer (Node has no XML parser), unique ids, every edge has a geometry child and valid `source` and `target`, only palette colors and the allowed fonts, node and edge caps, no label longer than 60 characters, no string that matches the secret scanner, every resource node has the ARM ID in a `tooltip` or attribute only if `--arm-ids` is on (default on for a private diagram, off for an exported copy). "Opens in draw.io" is a **manual** check (M-6); the engine exports with the draw.io desktop CLI when found, else reports the export as skipped, as the stacks generator does.
- **Reuse versus copy.** The stacks generator is manifest-driven and Terraform-specific; its theme tokens, icon map, contrast check and edit-detection hash are the reusable parts. Skills install independently, so `architecture-diagram` **ports** them (no cross-plugin import) and a parity test, skipped when the other plugin is absent, keeps the icon paths and the contrast function equal. Changing the stacks generator is out of scope.

### Decision 10. The questionnaire

For each check whose chain ends at `questionnaire`, and for every practice-only recommendation (RE:04, RE:09 restore tests, OE:01, OE:08, PE:01, PE:06 and similar), `waf.mjs questionnaire` writes `questionnaire.json` (id, pillar, WAF ID, question in pt-BR and English, allowed answers `yes`, `partial`, `no`, `unknown`, `not-applicable`, optional note, `evidenceHint`). The user answers in `questionnaire.answers.json` (or tells the agent, which transcribes with the answerer's role and date). An answer becomes a `statement` evidence (`reported`, Medium at most). Unanswered items are `not verified: unanswered` and stay in the report with the question text so the client can answer later. No answer is ever inferred by the model.

### Decision 11. The report in pt-BR

`assessment-report` renders pt-BR (`--lang pt-BR`, locale exists). Content specific to this skill goes where the schema allows: the executive `summary` (Markdown without headings; a coverage table per pillar is allowed as a table), the `decisions` list, the `frameworks` entry for `azure-waf` (version = the checklist page dates, date = read date, URL) with `controls: [{framework: "azure-waf", controlId: "SE:06"}]` on findings, checked against a **catalog file of IDs** the skill ships (`references/pillars.md` also holds the IDs; **no Microsoft text is copied**, only IDs and our own short titles, because the licence of the Learn text was not verified), and a separate `coverage.md` (engine-written, pt-BR) delivered next to the report and passed to `docs-generator` as an extra annex if the user wants DOCX or PDF. The report is rendered with `--unreviewed` by the agent and carries the stamp "not human reviewed"; after the user's explicit approval the main conversation runs `review --approve --by "<name>"` and `render` again. A schema extension of `assessment-report` for a coverage annex is a possible follow-up, not needed for v1.

**Answer key** (`key.json`): per planted flaw, the check ID, pillar, ARM ID, expected state and severity range; per pillar the expected coverage counts; per decoy (a compliant resource that looks similar) the expected `pass`. A scorer in code compares by check ID and ARM ID (not by text), like `assessment-evals`.

**Deterministic tests (run in CI, no network):** catalog schema and KQL allowlist (one failing fixture per rule); WAF IDs exist in the shipped ID list; paging and truncation; each error state; redaction (a planted secret-shaped value, a tag value, an `appSettings` block never appear in any file); manifest hashes and tamper detection; `map` output verified by `assess.mjs verify`; the cap table (each row of Decision 7); topology determinism (same input, same bytes); diagram checks (well-formed, unique ids, palette, caps, a 2,000-node input splits into pages and "+N more"); the guard (allow and deny shapes, namespaced `agent_type`, path rules for Write, the shapes list equal to the agent file); the pipeline `assessment.json` → pt-BR report (golden files, run through `docs-generator check`); the prompt-examples test; context budgets; CRLF and Windows path cases for the guard and engines (the repository has had Windows path bugs; tests use `path.win32` cases as `fix-engine-windows-paths` does).

A reporting template in the file lists exactly what may be shared (counts, states, tool names, error classes, durations) and what may not (names, IDs, tag values, screenshots without blurring).

**Acceptance criteria.** (1) The fixture run reproduces the key: every planted flaw found with the right check, every decoy `pass`, the invisible subscription reported as `scope-incomplete`. (2) No secret-shaped string, tag value outside the allowlist or Entra name in any output of the fixture run. (3) Every finding with a sealed line passes `assess.mjs verify`; a tampered line demotes. (4) The coverage statement per pillar is printed and its counts equal the manifest. (5) Two runs on the same fixture give byte-identical `topology.json` and `.drawio`. (6) `npm test`, `validate-skills`, `context-budget` and `openspec validate --all --strict` pass. (7) The agent's instructions pass the guard-equality test. **Stays "not verified" until the user's test:** the real MCP tool names and `--read-only` behavior (M-1, M-2), cross-plugin pre-loading (M-4), live guard behavior for this agent, behavior against real Resource Graph volume and throttling, Windows `az` spawn (M-8), real token use (M-7), and that the report is useful to the client.

## Cost and tokens of one run (estimate, not a measurement)

Premises, all explicit: one agent context; a tenant of 10 subscriptions and about 6,000 resources; a catalog of 120 checks (about 24 per pillar); about 90 tool turns; MCP exploration limited to 25 calls of about 1,500 tokens each; engine summaries of about 120 tokens per check; 40 findings of about 450 output tokens; pre-loaded context of about 8,100 tokens by the repository's own byte estimate (agent about 2,500, `azure-waf-review` about 2,200, `assessment-report` 2,060, `architecture-diagram` about 1,500; `estimate:bytes/4`, margin 30 percent not applied); prompt caching works so that the context is read from cache after the first turn.

| Quantity | Low (3 subs, 800 resources, 60 checks) | Mid (premises above) | High (50 subs, 50,000 resources) |
|----------|----------------------------------------|----------------------|----------------------------------|
| Tool turns | 40 | 90 | 130 |
| Fresh input tokens (never read before) | about 50k | about 110k | about 150k |
| Average context per turn | about 30k | about 60k | about 90k |
| Cached input re-read | about 1.2M | about 5.4M | about 11.7M |
| Output tokens | about 15k | about 30k | about 45k |

With **hypothetical** unit prices (input 3, output 15, cache read 0.1 times input, cache write 1.25 times input, all per million tokens in an arbitrary currency unit; the real prices must be read from the provider's pricing page on the day), the three columns come to about 0.8, 2.5 and 4.8 units. The model's tokenizer can change counts by about 30 percent (see `docs/aep/context-budget.md`). Collector wall time is separate and is not tokens: roughly 120 queries of 1 to 5 seconds plus paging, so minutes, bounded by Resource Graph throttling (not measured). The only claim that matters for design is the shape: **model tokens grow with the number of checks and the offender cap, not with the number of resources**; test M-7 measures it.

## Risks and residual limits

| # | Risk | Mitigation |
|---|------|------------|
| R1 | `--read-only` is a filter by annotation, documented on `main`, not verified for the pinned release | Pin; role that cannot write is the real boundary; M-1 lists tools; namespace allowlist; guard |
| R2 | The Learn security page says not to use a local MCP server with production data | Dedicated Reader identity, read-only, no Key Vault, no data plane, data statement, T2 mode; **Q1** asks the user to accept or choose |
| R3 | Resource Graph returns partial results silently when RBAC is partial | Visible-subscription count and consent; `scope-incomplete` state; canary check |
| R4 | The hook fails open and may not run (Node missing, plugin hooks disabled) | Layers: prompt rules, engine limits, role, `permissions.deny` snippet in the README; stated plainly |
| R5 | Windows: spawning `az.cmd` needs a shell | Constant argv only; tests; M-8; if it cannot be made safe, Windows uses T2 (user runs `collect`) |
| R6 | A catalog of checks is a maintenance burden and Microsoft changes recommendations | Each check records `docDate`; a test fails if a WAF ID is not in the shipped ID list; the report prints the catalog version; checks are a sample, never "the WAF" |
| R7 | False comfort: "no findings" read as "compliant" | Coverage statement per pillar; `pass` only when `evaluated > 0`; the report never says compliant |
| R8 | Prompt injection through resource names, tags and descriptions | Data-not-instructions rule; length and control-character limits; hostile fixture; JSON quoting; no tool the injected text could abuse beyond reads |
| R9 | Pre-loading across plugins may not work | Decision 1 plan B and C; M-4 |
| R10 | `@azure/mcp` needs Node 22; the repository's rule is Node 20 | State the prerequisite; the engines stay Node 20; `dnx`/`uvx`/Docker documented as alternatives (not verified) |
| R11 | The first `.mcp.json` in the catalog changes the supply-chain surface (an `npx` download at start) | Exact version pin and, if the maintainer wants, an integrity note in the README; no `latest` |

| R13 | The model can still mis-state a finding | The verifier proves provenance only; Critical needs `reverify`; the report says what the verifier does not prove; the user reviews before approving |

## Alternatives discarded

- **Use `azqr` as the engine.** It is a good source (APRL rules, many checks) but is a Go binary the user must install, its rules map to the Proactive Resiliency Library rather than to WAF IDs, and an assessment that hides its method behind one tool cannot state per-check coverage. Kept as an **optional additional source** through the MCP `extension azqr` when installed.
- **Rely on the MCP alone.** Fails the user's own criterion (claim 5) and the volume problem.
- **Use `az` freely from the agent.** Rejected: unbounded command surface, the very problem the guard history shows.
- **Mermaid diagrams.** Mermaid is not editable draw.io, and the user asked for draw.io; `azure-resource-visualizer` already covers Mermaid per resource group.
- **A numeric maturity or WAF score.** No validated rubric; invites false precision.
- **Model-written coordinates for the diagram.** Not reproducible or testable.
- **Sub-subagents per pillar.** Unverified capability; files as state are enough.
- **Putting findings text from Microsoft pages into the repository.** Licence not verified; IDs and paraphrased titles only.

## Questions for the maintainer (with a recommendation each)

- **Q1. Tenant data and a local MCP server.** The Learn security page advises against a local Azure MCP Server for production data. Accept the layered mitigation (dedicated Reader identity, read-only, namespace allowlist, no data plane) for this internal tenant? **Recommendation: accept, with a dedicated identity and the strict redaction mode available.**
- **Q2. Collector as the volume path.** Is it acceptable that bulk facts come from the collector (Resource Graph) and the MCP is used for what the collector cannot answer and for corroboration, because the MCP has no Resource Graph tool? **Recommendation: yes; the chain stays MCP first only for checks where it has an equivalent tool and the volume is small.**
- **Q3. Who runs the collector.** The agent through the guard (T1), or the user by hand (T2)? **Recommendation: T1 as the default and T2 as a documented fallback mode.**
- **Q4. Role and scope.** Reader plus Security Reader at the root management group, assigned to a dedicated identity, removed after the review? **Recommendation: yes; never elevated access.**
- **Q5. Pillars and order.** All five pillars with honest coverage, Security first? **Recommendation: yes, and a run may be limited to chosen pillars.**
- **Q6. Design system and severity colors.** May severity badges use a status color outside the project palette (contrast-checked, with a letter and a legend), or must they stay inside the palette? **Recommendation: allow status colors for badges only, never for panels.**
- **Q7. Anonymization.** Must the first version offer `--redact strict` (aliases, local map)? **Recommendation: spec it now, implement in PR 1 if the client or the user needs it; otherwise a follow-up.**
- **Q8. Windows.** Does the user run this on Windows? **Recommendation: if yes, run M-8 first; if the `az` spawn cannot be made safe, Windows uses T2.**
- **Q9. A general cap rule for tool output in `assessment-report`.** Adopt the Decision 7 table in a follow-up change to `assessment-report` for its `output` kind? **Recommendation: yes, after this change proves it on real data.**
- **Q10. Report extras.** Is `coverage.md` as a separate annex enough for v1, or should `assessment-report` get an `appendices` field? **Recommendation: separate file in v1.**
- **Q11. Optional `azqr`.** Support `extension azqr` as an extra source when installed? **Recommendation: yes, as optional and unsealed (`reported`).**
- **Q12. Plugin layout.** Option A (one plugin), with `architecture-diagram` extractable later? **Recommendation: yes.**
