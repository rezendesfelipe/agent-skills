## Decisions

### Decision 1. Packaging: one new plugin, with the agent and two skills

| Option | Pros | Cons |
|--------|------|------|
| **A. New plugin `azure-waf-review` with agent `azure-waf-reviewer` and skills `azure-waf-review` and `architecture-diagram` (recommended)** | Own version and release cadence. No coupling with Terraform tooling and its vendored `yaml`. The agent and the skills it pre-loads live in one plugin, as `stacks-auditor` does, so `skills:` resolves by the same mechanism. A `.mcp.json` and a guard hook belong to one plugin that a user installs knowingly | A second plugin of Azure content next to `azure-terraform-stacks` (naming clarity needed in the README); `assessment-report` is in a third plugin, so a cross-plugin dependency appears |
| B. Extend `azure-terraform-stacks` | One Azure plugin | The plugin is about IaC and repositories; this work is explicitly **without IaC**. Coupling releases (0.3.0 would carry an MCP declaration and a network-calling collector for people who only scaffold Terraform). A `.mcp.json` would start for every user of the plugin |
| C. Three plugins: `azure-waf-review`, `architecture-diagram` (generic) and the agent | Best reuse of the diagram skill | Three manifests and cross-plugin pre-loading twice, which is unverified (claim 10). The generic skill can be extracted later at low cost because skill names are unique across plugins |

**Cross-plugin dependency (assessment-report).** The agent must have the `assessment-report` skill pre-loaded, because the report pipeline is its engine. Two facts are unknown (claim 10): whether `skills:` can name a skill from another plugin, and what the plugin `dependencies` field guarantees. Plan: declare `"dependencies": ["assessment-report"]` in `plugin.json` (documented field) **and** test M-2 in a live session. **Plan B** if pre-loading fails: the agent keeps `Skill` out of `tools`, so it cannot call it; instead its first step reads `references/` of the skill by path through the same trusted-engine lookup that `stacks-auditor` uses, and the agent's budget is declared without the pre-loaded `SKILL.md`. Plan C (last resort, needs maintainer approval): move the three skills into one plugin. The `agent-skills` CLI installs a skill together with an agent that lists it (`add-custom-agents`), so the CLI path does not depend on plugin boundaries.

### Decision 3. The agent, its tools and how to limit them

The agent needs five capabilities: read files (`Read`, `Grep`, `Glob`), call the Azure MCP Server (read-only), run the engines of the skills, write `assessment.json`, and nothing else. Options:

| Option | What the agent holds | Pros | Cons |
|--------|---------------------|------|------|
| **T1. Guarded Bash for three fixed engines, guarded Write (recommended)** | `Read, Grep, Glob, Write, Edit, Bash, mcp__azure-waf__*` (the MCP entry matches nothing unless the user opted in to the optional server); a plugin `PreToolUse` guard: `Bash` allows only `node <waf.mjs> <sub>`, `node <assess.mjs> <sub>`, `node <diagram.mjs> build`, `ls -d`, `test -f/-d`, `node --version`; `Write`/`Edit` only inside `waf-review/<run>/`, never `collected/` or `.state/` | Same proven pattern as `stacks-auditor` (guard shapes, trusted-engine origin, no engine inside the audited root). The **catalog fixes what the collector can ask**, so the agent never composes an `az` or KQL string: the part of the old allowlist that took three review rounds (free path and argument shapes) shrinks to "subcommand names and `--out` inside the run folder" | Still the Bash tool and a hook that fails open if Node cannot start it or an administrator disables plugin hooks; three engines instead of one. Write is a new surface (path rules) |
| T2. No Bash: the collector is run **by the user**, the agent only reads files | `Read, Grep, Glob` plus MCP | Smallest surface; credentials and `az login` stay with the user | The report pipeline (`assess.mjs`) also needs a shell; the user would run 6 to 8 commands by hand. Defeats "an agent that verifies and brings results". Kept as the **fallback mode** (`--collect-only` by the user; the agent starts at "analyze") |
| T3. The collector as an own MCP server (one tool `collect(check_id)`) | `Read, Grep, Glob` plus two MCP servers | No Bash for collection; the tool schema is the allowlist | New code (JSON-RPC or an SDK dependency, which this repository avoids), a second long-lived process holding credentials, still Bash for `assess.mjs`. Deferred, not rejected: revisit when the catalog stabilizes |
| T4. The agent returns JSON in its final message and the main conversation writes the files | `Read, Grep, Glob` plus MCP | No `Write` for the agent | Puts the whole assessment in the main context, the opposite of isolation; loses incremental persistence |

**Does a fixed catalog avoid free Bash? Partly.** It avoids free *commands to Azure*: the agent cannot compose `az`, KQL or REST. It does not remove the need for the shell tool, so a guard remains. The honest gain is a much smaller and more testable guard (Decision 3, "Guard rules"), and no `az` in the guard's allowlist at all, because the engine spawns `az` itself with constant arguments.

**The `assess.mjs` subcommands the guard allows** are `status`, `init` (with `--root` fixed to `<run>/collected`), `inventory`, `verify`, `classify`, `check`, `review` **without `--approve`** and `finish`. `assess.mjs render` is **denied** to the agent: the only render it may run is `waf.mjs render` (which runs `seal-check` and `cap-check` first and then calls `assess.mjs render --unreviewed` with constant arguments, Decision 7). `review --approve` is denied on purpose (the skill says the agent never approves); it runs in the main conversation after the user's explicit yes, followed by a normal render. `capture` is not allowed because collected data is already sealed by the collector.

**Guard v2 (review round 1; the spec has the full list).** The guard acts only when `agent_type` is `azure-waf-reviewer` or `azure-waf-review:azure-waf-reviewer` and rejects shell metacharacters wholesale. The shapes are an **allowlist per subcommand of flag names and value formats** (modeled on `SHAPES` of `stacks-auditor-guard.mjs`); an unknown flag is denied. In particular: `--root` is accepted only as the real path `<run>/collected` (and only for `assess.mjs init`; denied for every other subcommand and value); `--out` and `--run` must resolve to the **current** run folder under `waf-review/` (another run is denied); denied everywhere: `--redact none`, `--stage`, `--az` and any path to `az`, `--catalog`, `--scope`, `--scope-file`, `--query-budget`, `--fixtures`, `--force`, `--approve`; the flags the agent may use are the allowlisted ones only, among them `--pillars <list>` (closed names) for `plan` and `collect`, `--run <current run>`, `--check <catalog id>`, `--resume`, `--json` and `--lang pt-BR` where the subcommand takes it; denied subcommands: `consent`, `reverify`, `purge`, `assess.mjs render`. Engines are accepted only after `realpath` from the plugin's skill folders or the user's skills folders, never inside the working directory or a `--root`. `Write` and `Edit` are allowed **only for two files of the current run folder: `assessment.json` and `questionnaire.answers.json`** (a closed list, which also closes the bypass of the agent writing its own `relatorio.md` with a Critical); every other path is denied, in particular `collected/`, `.state/`, `report/`, `consent.json`, `map.json`, `reverify/`, `severity-summary.json` and `.gitignore`. **`Read`, `Grep` and `Glob` are also guarded** (the stacks-auditor has them unguarded, see "Related, out of scope"): allowed only inside the current run folder and the skill folders; `~/.azure`, `~/.ssh`, `.env` files, `~/.claude/projects`, other runs, `/proc/*/environ` and the home directory outside the run are denied. `aliases.json` is written **outside the run folder**, in the user's state directory (`${XDG_STATE_HOME:-~/.local/state}/waf-review/<run-id>/aliases.json`, directory mode 0700, file 0600; `%LOCALAPPDATA%` on Windows), readable only by the user and by `waf.mjs`; the guard also denies that directory to `Read`, `Grep` and `Glob`. It is not under the tree a recursive `Grep` or `Glob` of the run folder can reach. How Claude Code's `Grep` and `Glob` report paths to the hook (the guard sees the `path` argument, not the files found) is **not verified**; a test proves that a recursive search over the run folder returns no alias file. If the hook is inactive (an older Claude Code or hooks disabled) the file is still outside the run folder but readable by any tool running as the user: documented residual. MCP calls: only the server `azure-waf`, only the exact tools of the `--tool` list, and any tool input that sets the global `Authentication method` to `key` or `connectionString` is denied (the exact parameter name is **not verified**; the guard denies any input key matching `auth` whose value is not `credential`). The shapes in the agent file are kept equal to the guard's list by a test.

**Hook failure mode (decision D5).** Facts read by the integrator at https://code.claude.com/docs/en/hooks (section "Block the action when a hook fails"; this author did not re-read it): without `onFailure`, a hook that fails or times out lets the action proceed; with `"onFailure": "block"` these count as failures: a hook that does not start (a missing script or executable), an exit code other than 0 or 2 (even with JSON that allows), a timeout and invalid JSON output; a failure then has the effect of exit 2 on the event (a `PreToolUse` blocks the call). It has no effect on `Stop`, `SubagentStop`, `TaskCompleted`, `TeammateIdle` and background hooks. The minimum Claude Code version is **2.1.295** (for `mcp_tool` hooks **2.1.328**); on an earlier version the field is ignored, which is fail-open, and the README states the minimum. There is a Windows note for installations without Git Bash that the integrator read and that must be repeated from the page at implementation.

*Trade-off, documented and recommended.* Plugin hooks fire for the **whole session**, and this plugin registers the guard for `Bash`, `Write`, `Edit`, `Read`, `Grep`, `Glob` and the MCP tools, each matcher also applying to the main conversation (the guard exits 0 when `agent_type` is not the agent's). With `block`, a guard failure (Node missing, a broken path after an update) therefore blocks **every read, write, search and edit of the session, not only Bash**, until the plugin is disabled; and because Bash is blocked too, the recovery goes through the `/plugin` interface (or by editing the plugin settings by hand outside the session). **Cost:** one Node process starts for every `Read`, `Grep`, `Glob`, `Edit`, `Write`, `Bash` and MCP call of the session (a startup latency per call, not measured; M-5 records it). Expected symptom: calls refused with a hook failure notice (the exact message is **not verified**; M-11). Recovery: disable the plugin in `/plugin`, fix the path or install Node, restart the session. **Recommendation (kept):** install and enable this plugin only in the dedicated audit WSL distro or profile (already required by the privacy plan), so a guard failure blocks that distro only; use the exec form (`command` plus `args`) so the plugin root path is one argument without shell quoting, which removes one class of path failure (not verified to remove the others). The same reasoning is registered as a follow-up for the `stacks-auditor` guard, **not changed in this change**.

**The Azure MCP is optional and is not shipped as a `.mcp.json`.** Decision Q1 makes the collector the production path, and a plugin `.mcp.json` starts its server whenever the plugin is enabled. The plugin therefore ships **no** `.mcp.json`; `references/azure-mcp-optional.md` documents the restricted configuration (server name `azure-waf`, so the tools are `mcp__azure-waf__*`) that the user adds to a user or project configuration only after validating it outside production (manual tests M-8 and M-9; **`--tool` with an exact list only**: no broad namespace such as `appservice`, `storage`, `monitor`, `sql` or `compute`, decision D3; user confirmation always on). Without it the agent has no MCP tools, the chain skips `mcp`, and the report states that. The `tools` entry `mcp__azure-waf__*` is harmless when no such server exists.

**Guard: what the independent reviewer should look at (three review rounds on `stacks-auditor`).**

- *Surface.* One script, `hooks/azure-waf-reviewer-guard.mjs`, registered for the matchers `Bash`, `Write`, `Edit`, `Read`, `Grep`, `Glob` and `mcp__azure-waf__.*`, with `"onFailure": "block"` (next subsection). Inputs: `tool_name`, `tool_input`, `cwd`, `agent_type`. It acts only for the two `agent_type` values and exits 2 with a reason to deny; every other caller gets exit 0. With `onFailure: block` a hook that cannot start, times out, exits with a code other than 0 or 2, or prints invalid JSON blocks the call (Claude Code 2.1.295 or later, as read by the integrator); in older versions the field is ignored and the guard **fails open**.
- *Allowlist.* Bash shapes: `ls -d`, `test -f/-d`, `node --version`, `node <waf-engine> <plan|collect|coverage|questionnaire|map|seal-check|cap-check|render|topology|status> ...`, `node <assess-engine> <status|init|inventory|verify|classify|check|review (no --approve)|finish> ...`, `node <diagram-engine> <build|check> ...`, each with its flag allowlist. Denied explicitly: `consent`, `reverify`, `purge`, `assess.mjs render`, `--fixtures`, `--force`, `review --approve`, and every flag not on the subcommand's list. Metacharacters and quotes are rejected wholesale (no shell parsing). Engines are accepted only from the plugin's own skill folders or the user's skills folders after `realpath`, never from the working directory or a `--root`. `--out` and `--run` must resolve under `waf-review/`. `Write` and `Edit`: `realpath` under `<cwd>/waf-review/` except `collected/`, `.state/`, `.gitignore`. MCP: only the server `azure-waf` and the allowlisted namespaces or tools.
- *Classes of defect found in the precedent that must be re-checked:* an engine path that ends right but lives inside the audited root (I1); a command allowed but unreachable from the agent's working directory (I2); the `agent_type` compared with the bare name while the harness sends the namespaced one (the guard was inert).
- *Differential tests* (to be written in PR 4): (1) the same inputs run through the `stacks-auditor` guard and this guard must give the same decision for every shape they share (metacharacter table, tilde, `..`, engine inside cwd, namespaced `agent_type`); (2) a **word-splitting oracle**: for every allowed command the test runs the real shell (`sh -c 'printf "%s\n" ...'` on Linux CI) and asserts that the words the shell produces equal the guard's tokens, and that inserting each forbidden character at each position flips the decision to deny; (3) a property test that any string with a forbidden character is denied; (4) path tests with symlinks, `..`, a symlinked `waf-review`, case-insensitive Windows paths and `path.win32` inputs; (5) a test that the shapes in the agent file equal the guard's list.
- *Not verified:* behavior in a live session for this agent (the namespaced `agent_type` value, that the `Write`, `Edit` and MCP matchers fire for a subagent, the exact key that carries the path in `tool_input`), a check-then-use race on symlinks, and the fail-open cases. The guard is one layer; the identity's role is the boundary.

**Output location and who writes.** Engines write the run folder `waf-review/<run-id>/` (`<run-id>` = UTC timestamp) under the working directory; `init` creates `waf-review/.gitignore` containing `*` (the folder ignores itself, so a private tenant dump cannot be committed by accident and no `.gitignore` edit is needed). The model writes only `assessment.json` (and its pillar fragments, if any) and `questionnaire.answers.json`; everything else is engine output. Layout:

```text
waf-review/<run-id>/
  .gitignore                      (engine; content "*")
  run.json                        (engine: scope, consent record, versions, catalog hash)
  collected/                      (collector only; model Write denied)
    manifest.json                 (sealed entries per check)
    <check-id>.jsonl              (one resource per line, redacted)
    summary/<pillar>.md           (engine-written, at most about 1,500 tokens each)
  coverage.json  coverage.md      (engine: per check and per pillar)
  topology.json                   (engine, from collected data)
  diagram/<level>-<name>.drawio   (architecture-diagram engine)
  questionnaire.json              (engine) and questionnaire.answers.json (user, or model transcribing the user)
  assessment.json                 (model, assessment-report schema)
  .state/ report/                 (assess.mjs)
```

### Decision 4. Context at tenant scale

The model must never hold the tenant in context. The design:

1. `waf.mjs plan` writes `run.json` from `consent.json` (the scope, the stage, the redaction level and the query budget the **user** chose in `consent`) and from the one flag the guard allows the agent, `--pillars <list>`, a comma-separated subset of the closed names `security,reliability,cost,operations,performance` (default all five; unknown names are refused). It lists the subscriptions **visible** to the identity again and compares them with `consent.json`. The user's count was confirmed at `consent` (**consent interrupt**). This also defends against the silent partial result of Resource Graph (claim 12): a lower count than expected is reported as `scope-incomplete`, not as a clean tenant.
2. `waf.mjs collect --pillar <p>` runs the catalog checks of one pillar: one Resource Graph query per check at tenant scope (management group scope or the subscription list), paging with `$skipToken` to disk, bounded by limits (Decision 5). It is **resumable** (`manifest.json` lists finished checks; `--resume` skips them) and idempotent.
3. The engine writes `summary/<pillar>.md`: per check, state, counts (evaluated, failing), the top 10 offenders (ARM ID, one key attribute) and the line numbers. That, not the raw data, is what the model reads. Drill-down uses `Read` with offset and limit on a JSONL file (one resource per line, so a line is a stable citation).
4. The model works **pillar by pillar** and persists after each pillar (`assessment.json` is updated with `Edit`); an interrupted run resumes from the file and the manifest. Findings for a failing check are drafted by `waf.mjs map` (deterministic: evidence entries, WAF reference, check ID) and the model adds impact, likelihood, rationale, recommendation and narrative.
5. Context cost is **sublinear in resources** by design: it grows with the number of checks and with the cap on offenders listed, not with resources. This is a design property to be measured (estimate below, test in manual run M-5).
6. Sub-subagents per pillar are **not** used: whether a subagent can spawn another was not verified, and one agent with files as state is simpler.

### Decision 5. The check catalog and the collector

**Chain order (decisions Q1 and Q2).** For production the chain starts at `collector` for every check the collector can answer, and always for volume and for everything the MCP does not cover. `mcp` appears in a chain only where the Azure MCP has an equivalent read-only command, comes **after** `collector`, is used only when the user opted in, and its answer is never the only basis of a High or Critical finding (cap table, Decision 7). Then `questionnaire`, then "not verified". No check depends on the MCP to be answered for production.

**Format** (`catalog/<pillar>.json`, JSON because the repository has no YAML dependency outside `azure-terraform-stacks`; a schema `catalog/check.schema.json` validates it):

```json
{
  "id": "SE-NET-001",
  "pillar": "security",
  "title": "Storage accounts allow public blob access",
  "waf": [{ "id": "SE:06", "framework": "azure-waf", "docDate": "2026-06-26", "url": "https://learn.microsoft.com/azure/well-architected/security/networking" }],
  "chain": ["collector", "mcp", "questionnaire"],
  "sources": {
    "collector": { "kind": "arg", "scope": "tenant",
      "evaluated": "resources | where type =~ 'microsoft.storage/storageaccounts' | summarize n=count()",
      "violations": "resources | where type =~ 'microsoft.storage/storageaccounts' | where properties.allowBlobPublicAccess == true | project id, name, subscriptionId, resourceGroup, location, publicAccess=tostring(properties.allowBlobPublicAccess)" },
    "mcp": { "namespace": "storage", "command": "account get", "equivalence": "per-subscription, partial" },
    "questionnaire": { "id": "Q-SE-NET-001", "text": "..." }
  },
  "proves": "The account setting that allows anonymous reads of blobs is on.",
  "doesNotProve": "That any container is actually public, or that data is sensitive.",
  "outputFields": [{"name":"id","type":"string"}, {"name":"name","type":"string"}, {"name":"subscriptionId","type":"string"}, {"name":"resourceGroup","type":"string"}, {"name":"location","type":"string"}, {"name":"publicAccess","type":"string"}],
  "redact": [],
  "limits": { "maxRows": 20000, "maxPages": 20, "maxParts": 40, "timeoutSec": 30 },
  "requires": ["Reader"],
  "severityHint": { "impact": "high", "note": "input to the model, not a severity" }
}
```

Rules: every check has a `waf` mapping (a WAF recommendation ID with the doc date) or the explicit value `"waf": []` with a reason (a landing zone or hygiene check); `outputFields` is a closed list (anything else the query returns is dropped); `violations` queries must pass an in-house **KQL allowlist** (starts with a documented table name, only read operators such as `where`, `project`, `extend`, `summarize`, `join`, `mv-expand`, `order by`, `take`; no `externaldata`, no `evaluate`, no `;` batches); `kind` is `arg`, `rest-get` (a fixed URL template with `api-version`, GET only) or `az-read` (an exact argument vector from the closed list, for example `az account list --all`; never "a read verb"), and the engine refuses any other kind; every catalog entry has a stable `id` and the catalog has a version and a SHA-256 recorded in `run.json`.

**Collector hardening (review round 1).**

- *Parts of at most 1 MiB (B1).* The engine writes each check as `collected/<check-id>.001.jsonl`, `.002.jsonl`, ... closing a part before it would pass 1 MiB (`MAX_FILE_BYTES` of the verifier is exactly 1 MiB; keep a margin of 8 KiB). A check with no row still writes an empty `.001.jsonl`, so `absence` evidence has a non-empty scope. `maxRows` is the cap on all parts together, `maxParts` the cap on parts. The manifest seals each part. Evidence cites a part and at most five lines of it.
- *`az-read` is a closed list of exact argument vectors (I6),* shipped in the catalog and short: `az --version`, `az account show`, `az account list --all`, and nothing else in v1. It is **not** "a read verb": `az account get-access-token`, `az keyvault secret show`, `az webapp config appsettings list`, `az functionapp config appsettings list`, `az storage account keys list` and `az acr credential show` are `get`, `show` or `list` and return secrets. A test fails for any argument vector outside the list and for any vector that contains a token-bearing verb. Every call adds `--only-show-errors`; `--debug` and `--verbose` are forbidden (they print requests and headers). The engine sets `AZURE_CORE_COLLECT_TELEMETRY=false` and starts `az` with an **environment allowlist** (`PATH`, `HOME`, `AZURE_CONFIG_DIR`, `LANG`, `LC_ALL`, `TERM`, `TMPDIR` and, only if already set, `HTTPS_PROXY`, `HTTP_PROXY`, `NO_PROXY`, `SSL_CERT_FILE`, `REQUESTS_CA_BUNDLE`); the provider and agent environment (for example any API key of the model provider) is **not** inherited. A test asserts the child environment equals the allowlist.
- *Output fields are typed scalars only (I7).* `outputFields` lists `{name, type}` with type `string`, `bool`, `number` or `enum`; a projection that yields an object, an array, `properties`, `tags` or a whole resource is rejected, and so is `tostring(properties.<object>)` (a test scans each `violations` query for these forms). Types that are **never projected**: Container Instances and Container Apps `env[].value`, Logic Apps `definition`, VM extension `settings` and `protectedSettings`, deployment `parameters` and `outputs`, App Service and Function settings, connection strings, automation variables, API Management named values, Key Vault and App Configuration values. The scalar projection is checked against the catalog's allow list of resource types per check.
- *No `take`, truncation (I11).* `take`, `limit` and `sample` are forbidden in catalog queries (Resource Graph then does not return `$skipToken` and sets `resultTruncated`, per the work-with-data page). A response with `resultTruncated=true` and no `$skipToken` is `not-verified:truncated`.
- *Throttling (I12).* The Resource Graph throttling headers (`x-ms-user-quota-remaining`, `x-ms-user-quota-resets-after`) are documented for the service, but whether **`az rest` prints them is not verified** (it probably does not without `--debug`, which is forbidden). The engine therefore uses **backoff on HTTP 429 or on a transient error** (bounded retries with increasing waits and a total wait cap), not a wait driven by a header.
- *All-or-nothing check (I13).* A check runs two queries on the **same scope**, `evaluated` and `violations`. A failure at any page of either (a 429 or timeout at page 3) ends the check as `not-verified:error` or `not-verified:timeout` with no partial `pass` or `fail`, and the partial parts are deleted. A **query budget** caps the run (initial value: 6,000 queries, enough for 50 subscriptions times 120 checks with paging; it is a premise, to be measured) and a run that reaches it stops with a partial result and the list of checks not done.
- *Path convention and scanner (I14).* The assessed root of `assess.mjs` is `<run>/collected/` and every evidence path is relative to it, `<check>.NNN.jsonl`. `absence` evidence uses the scope `<check>.*.jsonl`. `seal-check` verifies every part named in the manifest and the realpath of `scope.root`. The secret scanner runs on **values, not on field names**: a test with fields named `keyName`, `secretsEnabled` and `publicKeyAccess` must pass unredacted, and a real secret-shaped value in a field with an innocent name must be redacted.

**Result states per check:** `fail` (violations > 0), `pass` (evaluated > 0 and violations = 0), `not-applicable` (evaluated = 0, never reported as pass), `not-verified:no-permission` (HTTP 403 or a visible-scope mismatch), `not-verified:scope-incomplete`, `not-verified:no-api` (nothing in the chain can read it), `not-verified:timeout` (30 s query limit, retried once with a narrower scope per subscription; a failure on any page voids the check), `not-verified:truncated` (limit hit; offenders are a sample), `not-verified:error` (message class only), `needs-questionnaire`, `answered` (questionnaire).

**Execution.** `az` is spawned by the engine with `execFile` and **constant argument vectors** (no shell, no user input in an argument; the KQL goes in a request body file written by the engine), for example `az rest --method post --url https://management.azure.com/providers/Microsoft.ResourceGraph/resources?api-version=2022-10-01 --body @<file>`. The URL prefix is checked against an allowlist (`https://management.azure.com/`), the method against `GET` or the one documented read-only `POST` of Resource Graph, and a response is read, never stored raw (only redacted, projected fields are written). **No `az login` by the agent**: if there is no valid login the engine stops with exit 2 and the instruction for the user. Windows: spawning `az.cmd` needs special handling in Node (from the author's knowledge of Node security releases, **not verified here**: a `.cmd` cannot be started with `shell: false` on current Node versions); the engine resolves `az` and, only on Windows, starts it through the shell **with constant arguments**; this is risk R5 and manual test M-10.

**Sealing.** `collected/manifest.json` has, per check: `checkId`, `catalogSha256`, `querySha256` of both queries, `startedAt` and `finishedAt` (UTC), scope (`managementGroup` ID or subscription ID list hash), `visibleSubscriptions` count, pages, rows, `truncated`, and for **each part** its name, line count and SHA-256, the `az` version and the engine version. Raw API responses are not kept. The manifest is tamper-**evident** against accidents (hash checks), not tamper-proof against an actor with write access, like the existing gates; the guard keeps the model from writing `collected/`.

**Redaction (default, before anything is written):** properties known to carry secrets are never selected (`properties.siteConfig.appSettings`, connection strings, `primaryKey`, `secondaryKey`, SAS, `administratorLoginPassword`, certificate material); tag **keys** are kept and tag **values** are replaced by a short hash except for an allowlist of non-personal keys (`env`, `environment`, `tier`, `criticality`, `workload`, `costcenter`), since owner tags often hold e-mail addresses; every string value goes through the repository's secret scanner (`assessment-report` `scripts/lib/secrets.mjs` is the reference; the collector ships its own copy with a parity test) and a match replaces the value with `[redacted:<kind>]` and counts toward `redactions` in the manifest. Identity names appear only as principal IDs (ARM already returns GUIDs for role assignments; display names are not requested).

### Decision 7. Evidence, confidence and the cap for tool output

**Evidence for a sealed datum.** A failing check writes offenders as JSONL lines, in parts of at most 1 MiB (Decision 5); each line starts with the ARM ID. **Convention (I14):** the assessed root of `assess.mjs` is `<run>/collected/`; every evidence path is relative to it and names a part, `<check-id>.NNN.jsonl`. `waf.mjs map` produces, per failing check, an evidence entry of kind `file` of `assessment-report`: `path` = `<check-id>.NNN.jsonl`, `startLine`/`endLine` = at most five offender lines of that part, `quote` = those lines; a check with offenders in several parts yields one entry per part cited (at most three). The citation carries the ARM ID, the check ID and part (the file name), and the SHA-256 of the part (the verifier's `drift` check); the query and time are in `manifest.json` and are written in the finding text by `map`, **not** in `rationale` (the schema's `rationale` is `{impact, likelihood}` and nothing else is allowed). For "no resource violates", a check with `pass` and `evaluated` > 0 is cited as an `absence` evidence (scope `<check-id>.*.jsonl`, pattern `^\{"id":`), worded "not found in <scope>", never "does not exist"; each check writes at least an empty `.001.jsonl`, so the scope is non-empty (whether the verifier accepts an empty file is confirmed by a PR 1 test against the real `assess.mjs`). `assess.mjs verify` re-reads the lines: that is the deterministic verifier, unchanged. **Assessed root (B2):** `assessment.json` carries `scope.root`, written by the model; `waf.mjs seal-check` fails unless its `realpath` equals `<run>/collected` and every cited part matches the manifest, and the guard fixes `--root` (Decision 3). A negative test edits `scope.root` to a folder with a forged file and expects `seal-check` and `waf.mjs render` to refuse.

**What the verifier cannot do, and who can.** Re-running a query is a network call to a private tenant; **CI never does it, and `assess.mjs` has no network code**. "Re-verifiable by the user" is defined as: the user (not an agent) runs `waf.mjs reverify --check <id> [--resource <ARM ID>]` in their terminal, which re-runs the one catalog query, compares by ARM ID with the sealed lines and writes `reverify/<id>.json` with `state` equal to `match`, `changed` (fields differ), `gone` (no longer returned) or `error`, the user's UTC time and the hash of the part compared. The guard denies `reverify` to the agent. **The note lives in that separate file, not in `rationale`** (B3). **Gate in code (B3, confirmation round).** `waf.mjs cap-check` runs after `assess.mjs classify`. For every finding whose computed `severity` is `Critical` (the exact string is confirmed against `classify.mjs` in PR 1), it derives the **set of sealed checks from the evidence itself**: the check ID and part of every `file` evidence come from its **path** (`<check>.NNN.jsonl`), united with the checks the engine recorded for that finding in `map.json`. Three rules, all in code: (1) **empty is refused**: a Critical whose evidence yields no sealed check (for example one resting only on `statement` evidence, or on a part that is not in the manifest) is **refused**, so "all checks have a `match`" over an empty set can never pass; a model-written finding that cites `SE-001.001.jsonl` directly with no `map.json` entry is **not** empty, because the check `SE-001` is derived from the path, and then rule (2) applies; (2) for **each** derived check, `reverify/<check>.json` must exist with `state: match`; (3) the part hash recorded in that `reverify` file must equal the SHA-256 of the part **cited by the evidence** and the manifest hash of that part, otherwise refusal (a `reverify` of another version of the data does not release the finding). **Coverage of `match` (the definition):** a `reverify` run **without `--resource`** re-runs the whole check and `match` means every ARM ID of the sealed check's offenders is still returned with equal projected fields; a run **with `--resource <ARM ID>`** records `scope: resource` with the list of ARM IDs covered and releases a Critical **only if its covered ARM IDs include every ARM ID cited by the finding's evidence lines**; otherwise it is `partial` and does not release it. So `--resource` of one ARM ID never releases a check whose evidence cites N offenders unless all N are covered. `waf.mjs render` is the **only render the guard allows**: it runs `seal-check`, then `cap-check`, then calls `assess.mjs render --unreviewed` itself with constant arguments (the engine is located by the same trusted-origin rule), so the pt-BR report is produced by the existing renderer and a Critical without `reverify` cannot reach a report through the agent. The agent resolves a refused Critical by asking the user to run `reverify` or by honestly lowering impact or likelihood with a rationale. This is code in `waf.mjs`; **`assessment-report` is not changed (D1)**, so `assess.mjs render` run by a human directly is not gated (instruction only, see "Independent review, round 1").

**The cap rule (answers the pending item of `add-assessment-report-skill`: confidence cap for tool output).** Objective, in three lines, applied by the new skill's `map` step and checked by its tests:

| Evidence source | Evidence kind in `assessment.json` | Resulting confidence (by the existing rule) | Severity ceiling |
|-----------------|------------------------------------|---------------------------------------------|------------------|
| Collector-sealed JSONL line (manifest hash and catalog hash valid, produced by the engine, `collected/` not writable by the model) | `file` | `verified` | Any severity that `classify` computes, **except that Critical is refused at `waf.mjs render` unless `reverify/<check>.json` has `state: match`** (`cap-check`, in code) |
| MCP answer typed by the model (no file; the Azure MCP returns text into the context only) | `statement` with `source` `azure-mcp:<namespace>/<command>` and the call time | `reported` (one source) or `corroborated` (two independent sources) | Medium |
| Questionnaire answer by the user | `statement` with `source` the answerer's role | `reported` | Medium |
| MCP answer **and** sealed line for the same check and ARM ID | both | `verified` through the sealed line; the MCP item is listed as corroboration | as the sealed row |
| Nothing | none | `unverified`: only under "Not verified" | n/a |

Why this is defensible: the existing rule caps any non-machine-checked source at Medium and the verifier only proves provenance, not meaning. A sealed line is machine-checked *as a line of a file the model could not write*; it still does not prove the claim is a WAF violation (the catalog's `doesNotProve` text is printed in the finding). Critical requires a human-triggered re-execution because a wrong Critical finding about a production tenant costs most. The rule is local to this capability so `assessment-report` stays unchanged; the maintainer may adopt a general form for its `output` kind later (follow-up, Question Q9): "an `output`/`url` evidence is capped at `reported` unless a registered producer manifest seals it".

**Honesty limits (to print in the method annex).** The model's own tools (`Write`) are guarded, but the guard can fail open on an older Claude Code or when hooks are disabled (with `onFailure: block` it fails closed); the manifest hashes prove consistency, not that the collector ran. The report states: "Evidence sealed by the collector proves a line existed in a file produced at <time>; re-verification by the user is recorded when done." What is only instruction: see "Independent review, round 1".

### Decision 8. Security and privacy

- **Real tenant, minimal role, dedicated identity.** The identity that runs the collector (and the MCP, if enabled) holds **Reader** and **Security Reader** and nothing else: no Owner, no Contributor, no User Access Administrator. It is **separate from the user's daily account**, uses an **isolated Azure CLI profile** (`AZURE_CONFIG_DIR` pointing to a folder used only for this audit; honored by the Azure CLI, documented there, not read here, checked in M-0), and preferably has **temporary or PIM-activated access**. The role is assigned at the **root management group**, but only at the last step of the escalation below, by someone who holds Owner or User Access Administrator at that scope (the user's responsibility; this project never assigns roles). **Never** the "elevate access" route (it yields User Access Administrator, which can write). Reader does not reach data-plane content (no data actions, claim 16); Key Vault secret values and storage blobs need data roles and are never requested.
- **Escalation (decision Q4).** Stage 1: a **non-production** subscription or environment. Stage 2: **one production subscription**. Stage 3: the **root management group**. `consent --stage nonprod|one-prod|root-mg` (run by the user) records the stage in `consent.json`; moving to a later stage asks for a typed acknowledgment that the previous stage ran and was reviewed (a past run folder is looked up and cited when present). The consent screen shows the **expected subscription count (typed by the user) against the count actually read**; a difference is `scope-incomplete` and stops the run.
- **Consent produced by the user, outside the agent (decision D2).** `waf.mjs consent --stage nonprod|one-prod|root-mg --expected-subs <n>` is run **by the user in their own terminal**. It does the first Azure read itself (the identity, the subscriptions visible), shows: tenant ID (last 4 characters), identity type and role found, the resolved `az` path and whether an isolated profile is in use, the stage, the **typed expected count next to the count read** with names, the MCP status, and the statement that data passes through the model provider with or without the MCP; for stages 2 and 3 it asks for typed confirmations (provider retention and terms checked **by the user** against the company policy; security acceptance recorded). It writes `consent.json` with the SHA-256 of the exact text shown, the stage, the typed and read counts and the UTC time. `collect` and `plan` refuse to run without a valid `consent.json` for the run, and the stage comes from it (`plan --stage` is denied to the agent). The guard denies `consent` to the agent, and `Write` cannot touch `consent.json`. The agent can ask the user to run it; it cannot answer for them. No `--yes` flag. **Argument vectors of `consent` (N2):** it uses only entries of the catalog, the same closed lists as the collector: `az --version`, `az account show --output json`, `az account list --all --output json`, `az ad signed-in-user show --query id --output tsv` (a user) or `az ad sp show --id {guid} --query id --output tsv` (a service principal, `{guid}` validated by a GUID pattern from `az account show`), and two catalog `arg` checks through the fixed Resource Graph template: `CONSENT-SUBS` (subscriptions under the chosen management group, from `resourcecontainers`) and `CONSENT-ROLES` (the role assignments of the principal, from `authorizationresources`, the principal ID inserted into the request body, never into an argument). A test fails for any vector outside the list. Not verified: the output shape of the Graph reads and that the dedicated identity may read its own object; if the identity cannot be verified `consent` refuses unless the user types an acknowledgment, recorded. **Screen sanitization (N3):** subscription names, display names and every string shown by `consent` are controlled by whoever administers the tenant, so the screen strips or escapes control characters, ESC and ANSI CSI/OSC sequences and bidirectional controls (shown as `\u001b`); a test uses a subscription name containing ESC. **Tamper evidence (N4):** `consent.json` holds a hash of the shown text, not a signature; it is tamper-evident only. Like `aliases.json`, its protection from the model depends on the guard, so it is a documented residual risk when the hook is inactive. **Query budget (N6):** the initial cap of 6,000 queries is a premise to be measured, not a derived limit: 50 subscriptions times 120 checks times 2 queries is 12,000 if many checks time out and fall back to per-subscription scope, which exceeds it; the user sets the budget at `consent` (`--query-budget`, denied to the agent) and manual test M-5 measures the real count.
- **Data passes through the model, collector or not.** Everything the engine writes into a summary and everything the MCP returns is sent to the model provider as part of the conversation. **The collector does not remove this privacy risk; it removes the risks specific to the MCP** (see the next section). The README and the agent say it. The collector redacts before writing, but resource names, IDs, regions, SKUs, tag keys and network layout still pass through. Whether that is allowed, and under which retention and terms, depends on the company's policy and **must be checked by the user** before any production stage. If it is not allowed, the answer is `--redact strict` (specified now, decision Q7: names replaced by stable aliases `sub-01`, `vnet-03`; a local `aliases.json` maps back and never goes to the model) or the T2 mode, with the implementation scheduled by need.
- **Never in the output or the report:** secret values, keys, connection strings, SAS tokens, certificates, Key Vault contents, storage content, database rows, application settings values, tag values outside the allowlist, Entra user or group names, e-mail addresses, IP addresses of end users (public IP resources of the tenant are infrastructure and stay, behind `--redact strict` they are aliased). `assess.mjs render` already refuses a secret pattern; the collector's scan runs first.
- **Files stay local and out of git.** `waf-review/` ignores itself; the README says to keep it **inside the Linux filesystem of the audit distro, never under `/mnt/c` and never in a OneDrive or other synced folder**; `run.json` has a `retention` note and `waf.mjs purge --run <id>` deletes a run folder (confirmation required, user only; denied to the agent).
- **Privacy plan, user's preparation (decision D4).** A **separate WSL distro** only for the audit, minimal inherited environment (no provider or cloud keys in the shell profile), the provider's **retention and terms checked by the user** (the user's item, not this project's), and **cleanup of `~/.claude/projects` of the audit distro after each run** (the Claude Code transcripts of the session hold what the model saw; their retention is **not verified** and the cleanup is a documented user step with the exact folder to remove, not code this project runs). Residual risk: the transcripts and the provider's own retention exist until the user removes them and as the provider's terms allow.
- **Security Reader reaches more than configuration (I8).** From the built-in role page (read 2026-11-25), `Security Reader` includes `Microsoft.operationalInsights/workspaces/*/read` ("View log analytics data"), `Microsoft.Support/*/read` (support tickets) and `Microsoft.Resources/deployments/*/read` (deployment history), besides `Microsoft.Security/*/read` and `Microsoft.Authorization/*/read`. The collector's catalog **never queries** those resources, but the identity can; so the risk is real if the identity or the model is misled. Mitigations: ephemeral or PIM access removed after the review; the optional MCP never enables `monitor` in production; the guard denies the model any call outside the catalog; Reader alone is used for stages where Security Reader is not needed; the report lists the exposure.
- **Final message of the subagent (I4).** The subagent's last message goes into the parent conversation, so it is a channel for injection and for leaks. **The counts by severity, by confidence and by `not-verified` reason come from the engine, not from the model:** `waf.mjs status --json` (read from `report/report.json` and the manifest after `waf.mjs render` passed `cap-check`) prints them, and the final message template copies those numbers; the model does not type them. It contains **only fixed fields and counts**: the run ID, paths, the five pillar counters, counts by severity, counts by `not-verified` reason, the tool and catalog versions, and booleans (`mcpUsed`, `commandDenied`, `humanReviewed:false`); every name, resource ID or string from the tenant is **JSON-quoted** and capped at 60 characters, and **no free text from the tenant** is placed in prose. A test feeds a hostile tag and a hostile resource name and asserts the final message template contains neither as prose. Worst concrete scenarios (all assumed, none observed): (1) a string in a tag or name makes the agent read a token (`~/.azure`, `az account get-access-token`); (2) the model edits `assessment.json` to forge a `verified` Critical (`scope.root`); (3) the model skips consent or runs `consent`; (4) the model omits or downgrades findings; (5) an instruction in the final message steers the parent agent. Controls: the guard's Read and Bash allowlists and the closed `az-read` list (1), `seal-check`, `cap-check` and the render wrapper (2), consent by the user (3), the coverage counts computed by code from the manifest and the finding count printed from `assessment.json` (4: omission is visible, not prevented), the fixed-field final message (5).
- **Untrusted input.** Names, tags, descriptions, policy display names and alert text are attacker-controllable strings. The skill states they are **data, never instructions** (aligned with `references/read-only-and-untrusted-input.md` of `assessment-report`); the collector strips control characters and caps string length to 256; the summaries quote strings inside JSON, not as prose; a test plants an instruction-like tag value and checks that the pipeline output does not obey it. The Azure documentation itself says to treat tool descriptions and responses as untrusted.
- **No writes, no login.** The collector can only issue catalog reads; the agent never runs `az login` and the engine refuses to run without an existing login; if the MCP is enabled by the user it starts with `--read-only` and a closed `--namespace` list (no `keyvault`, `appconfig`, `storagesync`, `sreagent`, `deploy`, `extension` unless `azqr` is enabled by the user, `foundry*`, `communication`) or, stricter, with `--tool` fixing the exact tools (documented as not combinable with `--namespace`), with user confirmation (elicitation) **on**, and no `--dangerously-*` option is ever documented or passed (a test greps the optional configuration text).
- **Diagram severity source.** The L0 severity badges of `architecture-diagram` read severity only from `severity-summary.json`, which `waf.mjs cap-check` writes **only when it passes** (derived from `assessment.json`, the manifest hash and the `reverify` files). `waf.mjs topology` copies from it; `diagram.mjs build` omits severity badges when the file is missing or its recorded hash differs from `assessment.json`. A Critical refused by `cap-check` therefore never appears as a badge.
- **Residual risk named.** `--read-only` filters by tool annotation; a mis-annotated tool, a server bug or a beta version could still write. Mitigations: exact version pin, a role that cannot write (the real boundary), the exact `--tool` list, the guard, and the manual test M-8 that lists the exposed tools in the pinned version. The real guarantee is the **role**, not the flag. The optional MCP uses **`--tool` with an exact list only (D3)**: `azmcp_subscription_list`, `azmcp_group_list`, `azmcp_group_resource_list`, `azmcp_advisor_recommendation_list`, `azmcp_policy_assignment_list`, `azmcp_role_assignment_list` and `azmcp_resourcehealth_availability-status_get` are the **candidate names derived from the documented pattern** (only `azmcp_subscription_list`, `azmcp_group_list` and `azmcp_storage_account_get` appear verbatim in the documentation); the exact names come from `tools list` (M-8). No `storage`, `compute`, `appservice`, `sql`, `aks`, `monitor` or `keyvault` tool is on it. Elicitation is never disabled. The global parameter `Authentication method` (`key`, `connectionString`) is denied by the guard.

### Impact of the alert and workaround (Impacto do alerta e contorno)

The Learn security page advises against a local Azure MCP Server for production data and credentials (claim 7). It is guidance, not a technical block, and the page gives no reason. The user's decision (Q1 = A) is a **conscious deviation limited to an optional, restricted MCP validated outside production**; the collector is the production path.

| Risk | Where it comes from | What it affects | Covered by workaround |
|------|--------------------|-----------------|-----------------------|
| R-A. Deviation from the vendor's guidance | Local MCP with production data | Supportability and audit position of the company | 1, 3, 4, 7 |
| R-B. Prompt injection through tenant metadata | Names, tags, descriptions, alert text in MCP answers and collector output; the page itself says tool descriptions and responses are untrusted | The model could be steered to misreport or misuse a tool | 1, 3, 5, data-not-instructions rule, hostile-tag test |
| R-C. Tools annotated `Secret` | `keyvault secret get`, App Service app settings, `insights get` | Secrets forwarded to the model and logs | 3 (closed namespaces, no keyvault or appconfig), 1, 6 |
| R-D. Reach of the root management group | One identity reading the whole tenant | A mistake or a compromised session sees everything | 2, 8 |
| R-E. Data passes through the model provider | All summaries and answers, **collector included** | Retention, terms and company policy | 6 (`--redact strict`, no data plane), 7 (record), user's own check before production |
| R-F. Silent change of the server or a fixed version | A new release changes tool schemas ("rug pull"), the `latest` tag is a beta | Behavior not reviewed | 4 |

The eight workarounds:

1. **Collector as the main path** (decision Q1): fixed catalog, read-only, no free command, sealed output; the MCP is not needed for any production read.
2. **Dedicated identity**, separate from the daily account: isolated `AZURE_CONFIG_DIR` profile, only Reader and Security Reader, no Owner or Contributor, preferably temporary or PIM access.
3. **Restrictive MCP configuration** (opt-in): `--read-only`, `--namespace` with a closed list without `keyvault` and `appconfig`, or `--tool` fixing the exact tools, user confirmation on, elicitation never disabled.
4. **Pinned version**, never `@latest` (its `latest` tag is a prerelease), and a **review of the tool schemas at each update** with re-approval before use.
5. **Sandbox**: for the MCP, a container or distro with restricted filesystem and network; for the whole audit, a separate WSL distro (next section).
6. **Redaction** (`--redact strict`, decision Q7) and **no data plane** (no secret values, blobs, rows).
7. **A recorded decision** (ADR or an exception record for the conscious deviation, plus a security or compliance acceptance, including the model provider's retention and terms). The skill ships `references/decision-record-template.md`; the record lives with the user, not in this repository.
8. **Staged escalation**: non-production, then one production subscription, then the root management group.

**What the collector does not remove:** the privacy risk of data passing through the model (R-E) and the prompt-injection risk from tenant strings (R-B). It removes the risks specific to the MCP: the vendor's production warning (R-A), `Secret`-annotated tools (R-C), and an unreviewed server or schema (R-F).

### Platform: WSL (decision Q8)

The user works on Windows **and** on Ubuntu under WSL. The **main test platform is Ubuntu on WSL**: `az` is a real Linux binary and the engines never need a shell to start `az.cmd`. Native Windows is secondary (manual test M-10). Facts below were **relayed by the integrator from https://learn.microsoft.com/windows/wsl/wsl-config; this author did not re-read that page**:

- By default WSL appends the Windows `PATH` (`[interop] appendWindowsPath=true`) and runs Windows processes (`[interop] enabled=true`), so `az` may resolve to the Windows `az.cmd` (another login and shell); and `[automount] enabled=true` mounts `C:\` at `/mnt/c`.
- For the audit, `/etc/wsl.conf` should contain `[interop] enabled=false`, `appendWindowsPath=false` and `[automount] enabled=false`, with the **Azure CLI installed inside Ubuntu** and, preferably, a **separate distro used only for the audit** (the setting breaks `explorer.exe` and `code .` in that distro). Changes apply only after the distro restarts (about 8 seconds; `wsl --terminate` or `wsl --shutdown`).
- The commands that create the separate distro (`wsl --export` and `wsl --import`) and the way to install the Azure CLI in Ubuntu were **not verified**: the manual test says "check the documentation".
- Engine behavior: `consent` resolves `az` on `PATH` and **refuses** a path under `/mnt/` or ending in `.exe` or `.cmd` when it runs inside WSL, unless the user types an acknowledgment that is recorded; it prints the path in the consent screen. It never sets or reads a Windows profile.

### Decision 9. The diagram skill

- **Format:** a draw.io `mxfile` with one `<diagram>` page per view, uncompressed XML, edges always expanded, ids derived from a hash of the ARM ID (a regeneration gives a minimal diff), `html=1`, no XML comments (rules in `get_drawio_reference` and in `azure-terraform-stacks/references/diagram.md`).
- **Levels (so a tenant stays legible):** **L0 Landscape**: tenant → management group tree → subscriptions as cards (resource count, finding counts by severity, coverage badge). **L1 Subscription** (one page per subscription, capped at the 12 largest plus an "others" aggregate): resource groups collapsed into containers with resource-type counts and the top N resources by finding count. **L2 Network**: hub-spoke view across subscriptions: VNets with subnets, peerings (edges), gateways and firewalls, Private Endpoints and Private DNS zones, derived from `resources` and `networkresources`. Optional **L3 Workload** only if the plan names a tag key that groups resources. Hard caps: 80 nodes and 120 edges per page (an assertion in the generator); beyond the cap a "+N more" node with the count is drawn and the full list goes in `topology.json`.
- **Deterministic layout by script, not by the model.** A tenant diagram is the kind where model-placed coordinates drift, overlap and differ between runs. The generator places nodes by a layered algorithm (tree rows for MG levels, grid columns for children, fixed 10 px multiples) so the same `topology.json` always yields the same bytes. The model is allowed to choose the level, the title and short annotations through `topology.json` fields; it never writes coordinates. Layout by model is **rejected** (not reproducible, not testable) except for an optional "polish" pass the user may request.
- **Design system** (from the project `CLAUDE.md`): `background #0b1326` with `adaptiveColors="none"`; surfaces `#171f33` and `#222a3d`; borders `#45464d`; text `#dae2fd`, secondary `#c6c6cd`; accents `#2fd9f4`, `#7bd0ff`, `#5bbfae`, `#8dc63f`; fonts `Space Grotesk` for titles and `Manrope` for text, `Geist Sans` fallback (draw.io `fontFamily` takes one name, so the label style sets `fontFamily=Manrope` and the fallback is documented in the legend and the file `<diagram>` name; if the user lacks the fonts the editor substitutes). Rounded panels (`rounded=1;arcSize=8`), the discreet cyan glow of the design system has no draw.io style key that was verified here, so it is approximated by `strokeColor=#2fd9f4;strokeWidth=2` on the highlighted container (a documented approximation). Contrast is checked by the same WCAG routine as the stacks generator (text ≥ 4.5:1 on surfaces).
- **Severity colors.** The project palette has accents but no red or amber. Severity is encoded by a **badge letter and fill step inside the palette** (`C`, `H`, `M`, `L` in four accent or surface steps) and by line style, never by color alone; the user decided (Q6) that a status color outside the palette is allowed **for severity badges only**, contrast-checked and listed in the legend.
- **Icons.** A closed map from resource kind to a built-in `img/lib/azure2/...` stencil, ported from `azure-terraform-stacks/diagram/icons.json` for the kinds used by the catalog; a parity test fails if a path in the new map is absent from the stacks map or from draw.io's own library list when available; an unknown kind draws a labeled rounded box (never a guessed shape, which renders blank). `search_shapes` returned styles with external `https://app.diagrams.net/...svg` URLs; the generator uses the built-in `img/lib/azure2` relative paths so the file works offline in the desktop app and sends no tenant data anywhere. The Azure icon terms apply (do not reshape icons).
- **Validation** (`diagram.mjs check`): well-formed XML by an in-house tokenizer (Node has no XML parser), unique ids, every edge has a geometry child and valid `source` and `target`, only palette colors and the allowed fonts, node and edge caps, no label longer than 60 characters, no string that matches the secret scanner, every resource node has the ARM ID in a `tooltip` or attribute only if `--arm-ids` is on (default on for a private diagram, off for an exported copy). "Opens in draw.io" is a **manual** check (M-4); the engine exports with the draw.io desktop CLI when found, else reports the export as skipped, as the stacks generator does.
- **Reuse versus copy.** The stacks generator is manifest-driven and Terraform-specific; its theme tokens, icon map, contrast check and edit-detection hash are the reusable parts. Skills install independently, so `architecture-diagram` **ports** them (no cross-plugin import) and a parity test, skipped when the other plugin is absent, keeps the icon paths and the contrast function equal. Changing the stacks generator is out of scope.

### Decision 10. The questionnaire

For each check whose chain ends at `questionnaire`, and for every practice-only recommendation (RE:04, RE:09 restore tests, OE:01, OE:08, PE:01, PE:06 and similar), `waf.mjs questionnaire` writes `questionnaire.json` (id, pillar, WAF ID, question in pt-BR and English, allowed answers `yes`, `partial`, `no`, `unknown`, `not-applicable`, optional note, `evidenceHint`). The user answers in `questionnaire.answers.json` (or tells the agent, which transcribes with the answerer's role and date). An answer becomes a `statement` evidence (`reported`, Medium at most). Unanswered items are `not verified: unanswered` and stay in the report with the question text so the client can answer later. No answer is ever inferred by the model.

### Decision 11. The report in pt-BR

`assessment-report` renders pt-BR (`--lang pt-BR`, locale exists). Content specific to this skill goes where the schema allows: the executive `summary` (Markdown without headings; a coverage table per pillar is allowed as a table), the `decisions` list, the `frameworks` entry for `azure-waf` (version = the checklist page dates, date = read date, URL) with `controls: [{framework: "azure-waf", controlId: "SE:06"}]` on findings, checked against a **catalog file of IDs** the skill ships (`references/pillars.md` also holds the IDs; **no Microsoft text is copied**, only IDs and our own short titles, because the licence of the Learn text was not verified), and a separate `coverage.md` (engine-written, pt-BR) delivered next to the report and passed to `docs-generator` as an extra annex if the user wants DOCX or PDF. The report is rendered with `--unreviewed` by the agent and carries the stamp "not human reviewed"; after the user's explicit approval the main conversation runs `review --approve --by "<name>"` and `render` again. A schema extension of `assessment-report` for a coverage annex is a possible follow-up, not needed for v1.

| Quantity | Low (3 subs, 800 resources, 60 checks) | Mid (premises above) | High (50 subs, 50,000 resources) |
|----------|----------------------------------------|----------------------|----------------------------------|
| Tool turns | 40 | 90 | 130 |
| Fresh input tokens (never read before) | about 50k | about 110k | about 150k |
| Average context per turn | about 30k | about 60k | about 90k |
| Cached input re-read | about 1.2M | about 5.4M | about 11.7M |
| Output tokens | about 15k | about 30k | about 45k |

With **hypothetical** unit prices (input 3, output 15, cache read 0.1 times input, cache write 1.25 times input, all per million tokens in an arbitrary currency unit; the real prices must be read from the provider's pricing page on the day), the three columns come to about 0.8, 2.5 and 4.8 units. The model's tokenizer can change counts by about 30 percent (see `docs/aep/context-budget.md`). Collector wall time is separate and is not tokens: roughly 120 queries of 1 to 5 seconds plus paging, so minutes, bounded by Resource Graph throttling (not measured). The only claim that matters for design is the shape: **model tokens grow with the number of checks and the offender cap, not with the number of resources**; test M-5 measures it.

## Alternatives discarded

- **Use `azqr` as the engine.** It is a good source (APRL rules, many checks) but is a Go binary the user must install, its rules map to the Proactive Resiliency Library rather than to WAF IDs, and an assessment that hides its method behind one tool cannot state per-check coverage. Kept as an **optional additional source** through the MCP `extension azqr` when installed.
- **Rely on the MCP alone, or make it the production path.** Fails the user's own criterion (claim 5), the volume problem and the vendor's production guidance (decision Q1).
- **Ship a plugin `.mcp.json`.** It would start the server whenever the plugin is enabled; replaced by an opt-in document.
- **Use `az` freely from the agent.** Rejected: unbounded command surface, the very problem the guard history shows.
- **Mermaid diagrams.** Mermaid is not editable draw.io, and the user asked for draw.io; `azure-resource-visualizer` already covers Mermaid per resource group.
- **A numeric maturity or WAF score.** No validated rubric; invites false precision.
- **Model-written coordinates for the diagram.** Not reproducible or testable.
- **Sub-subagents per pillar.** Unverified capability; files as state are enough.
- **Putting findings text from Microsoft pages into the repository.** Licence not verified; IDs and paraphrased titles only.
