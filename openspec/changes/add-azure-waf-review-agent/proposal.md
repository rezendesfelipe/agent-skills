## Why

A consultant (here: the owner of the repository, for an internal client) needs a Well-Architected review of a real, private Azure tenant that has **no infrastructure as code and no diagrams**. Today this repository has the pieces but not the path:

- `azure-terraform-stacks` and its `stacks-auditor` read **repositories**, not a live tenant.
- `assessment-report` turns evidence into a verified report, but its evidence is files in a folder; nothing produces such files from Azure.
- Other clouds may have Well-Architected review skills (an earlier survey in this repository said AWS and Google do; that claim was **not re-verified**, and `awslabs/agent-plugins` showed none). For Azure the closest public work is `microsoft/azure-skills` (read 2026-11-25), which has `azure-compliance` (runs `azqr` plus Key Vault expiry checks), `azure-resource-visualizer` (Mermaid diagrams of one resource group) and `azure-diagnostics`, but **no Well-Architected review**, no tenant-wide scope, no draw.io, no coverage statement and no verifiable evidence.

Reading a whole tenant has three problems that a prompt alone does not solve:

1. **The Azure MCP Server does not cover everything, and its own documentation advises against it for production.** Its command reference on `main` (read in full, 2026-11-25) has no generic Resource Graph query, no Defender for Cloud (secure score, assessments), no policy compliance state (only `policy assignment list`), no management-group hierarchy and no network namespace (VNets, NSGs, peerings, firewalls). The Learn security page says: "Don't use a local Azure MCP Server to handle production data or production credentials." (guidance, not a technical block; the page does not explain the reason). The user's instruction is: "what the MCP does not cover and you need, create a way to verify it", and the user chose to make the **fixed-catalog collector the main path for production** and the MCP **optional, restricted and validated first in non-production** (decision Q1).
2. **Volume.** A tenant has thousands of resources. Raw MCP output in the model's context does not scale; a deterministic collector that writes to disk and returns summaries does.
3. **Trust.** A finding about a customer environment must point at evidence that code can check, and a check that could not run must say so, not pass.

## What Changes

- **New plugin `azure-waf-review`** (`plugins/azure-waf-review/`) with:
  - **Agent `azure-waf-reviewer`**: a read-only subagent in an isolated context that pre-loads the skills below, reads the tenant through the **deterministic collector** (main path) and, only when the user opted in after validating it outside production, also through the **Azure MCP Server in read-only mode**, and returns a summary and the paths of three artifacts: `assessment.json`, an editable **draw.io** architecture diagram, and a **pt-BR Well-Architected report** (stamped "not human reviewed" until the user approves). The design never depends on the MCP to touch production.
  - **Skill `azure-waf-review`**: the procedure, the rubric, a **fixed check catalog** (id, pillar, WAF recommendation ID with doc date, source chain, query, what it proves), the **collector** (`scripts/waf.mjs`, Node 20, no dependencies, read-only) and the **coverage matrix** per check and per pillar.
  - **Skill `architecture-diagram`**: generic and reusable; turns a topology JSON into a layered draw.io file (tenant, subscription, network levels) with a deterministic layout and the design system of the project (`CLAUDE.md`).
  - **No `.mcp.json` is shipped by default** (so the server does not start automatically). The restricted, pinned MCP configuration is a documented opt-in file (`references/azure-mcp-optional.md`) that the user copies after validating it in a non-production environment; `hooks/hooks.json` carries a `PreToolUse` guard for this agent only (Claude Code only; layered, never a guarantee).
- **Coverage with a fallback chain, per check:** collector with a fixed catalog (Resource Graph KQL, read-only REST GET, fixed-argv `az` reads) first for volume and for everything the MCP does not cover → Azure MCP (read-only, optional, only where it has an equivalent tool and only after non-production validation) → questionnaire answered by the user → **"not verified"**, with the reason (`no-permission`, `no-api`, `timeout`, `scope-incomplete`, `unanswered`). The report has a coverage section per pillar that states what was and was not checked.
- **Evidence and confidence.** Every collected datum is a line of a JSONL file under `collected/`, sealed by a manifest (check ID, catalog hash, query hash, UTC time, ARM IDs, SHA-256). The existing `assessment-report` verifier checks the lines as `file` evidence. Data typed by the model from an MCP answer is recorded as a `statement` and capped at `reported` (Medium at most). A sealed finding may be Critical only after the user re-ran the one query (`reverify`). The change does **not** modify `assessment-report`.
- **Privacy by construction and staged exposure.** A dedicated identity separated from the daily account (isolated `AZURE_CONFIG_DIR` profile, Reader plus Security Reader only, no Owner or Contributor, preferably temporary or PIM access), assigned at the root management group only after escalating from non-production to one production subscription; explicit consent before collection that shows the expected versus read subscription count; redaction of secrets, keys, connection strings, tag values and application data (`--redact strict` with aliases specified now); an output folder that ignores itself in git; and a statement that the data passes through the model provider **even with the collector** (the collector removes the MCP-specific risks, not the privacy risk). Section "Impact of the alert and workaround" of `design.md` lists the risks and the eight workarounds.
- **Platform.** The main test platform is **Ubuntu on WSL** (a real Linux `az`, no `az.cmd` without a shell); native Windows is secondary. The audit distro should have Windows interop and automount disabled (`design.md`, "Platform: WSL").
- **Hardening after the independent review (round 1) and the user's decisions D1 to D5.** The collector splits evidence into parts of at most 1 MiB (the verifier's limit); `waf.mjs` seals the assessed root, gates Critical findings on a user-run `reverify` in code (`cap-check`) and is the only renderer the guard allows; consent is produced by the user (`waf.mjs consent`) outside the agent; the guard uses flag allowlists, guards reads and fixes `--root`; hooks use `"onFailure": "block"`; `az-read` is a closed list of exact vectors; outputs are typed scalars; the optional MCP uses an exact `--tool` list; and `assessment-report` is **not changed**, so what cannot be enforced without changing it is written as instruction only (`design.md`, "Independent review, round 1").
- **Tests without the tenant:** a synthetic tenant "Contoso Exemplo" (2 subscriptions, planted flaws, an answer key), deterministic tests for the catalog, collector, topology, diagram and the `assessment.json` → pt-BR report pipeline, and a **manual test script for the user** to run on the real tenant, with a way to report results without exposing client data.
- **Example prompts** (permanent rule) in `references/prompts.md` of the skill (section `## Agent: azure-waf-reviewer`), English and pt-BR, four positive examples and anti-examples.
- Delivery in five small pull requests, the first being the catalog, collector and fixtures with no tenant and no MCP; the release (versions, tag, npm) stays out of this change and needs the maintainer's explicit OK.

## Non-goals

- Implementing anything in this pull request: it adds only `openspec/changes/add-azure-waf-review-agent/`. No skill, agent, plugin, hook, workflow, `README.md`, `.claude-plugin/marketplace.json`, `package.json` or `docs/aep/context-budgets.json` is touched.
- **Changing the tenant, ever.** No write call, no remediation, no pull request against the tenant, no policy assignment, no Advisor recommendation update (`advisor recommendation update` exists in the MCP and is filtered by `--read-only`). The agent recommends; it does not apply.
- Microsoft Entra ID (users, groups, Conditional Access, PIM, MFA, app registrations). Azure RBAC and Entra roles are separate systems and reading Entra needs the Microsoft Graph API and other roles (design, "Not verified"). v1 records identity checks that need Entra as `not verified: no-api` or as questionnaire items.
- Application code, data-plane content (blob contents, Key Vault secret values, database rows, queue messages) and logs with user content. The collector reads configuration, not data.
- Costs in money (Cost Management API, invoices, reservations utilization). v1 uses Advisor and Resource Graph signals for the Cost Optimization pillar and marks the rest `not verified`.
- Other clouds. AWS and Google follow only if this works and the maintainer asks (and only after the survey claim about their skills is verified at the primary source).
- Multi-tenant or Lighthouse scope, sovereign clouds and a hosted or remote Azure MCP Server. One tenant, public cloud, local server (and the server is optional).
- A numeric maturity score. The report states coverage and findings, never a score.
- An own MCP server for the collector (considered and deferred, design Decision 3), and making the Azure MCP Server required for any production read.
- Changing `assessment-report`, `docs-generator`, `azure-terraform-stacks` or its diagram generator. They are reused; any gap found becomes a separate change.
- A release: no version bump, no tag, no npm publish (gate 2).
